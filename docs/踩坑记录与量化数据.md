## 二、依赖与版本类

### 1. Spring Boot 4.1 + MyBatis-Plus 3.5.13 启动即崩

**现象**：`mvn compile` 通过，一启动就 `NoSuchMethodError: PropertyMapper.alwaysApplyingWhenNonNull()`。

**根因**：MyBatis-Plus 3.5.13 调用的这个方法在 Spring Boot 4.1 已被移除（换成了 `alwaysApplying`）。

**教训（面试点）**：**「编译通过」不等于「能启动」**。M1 阶段我只跑了 compile 就认为骨架没问题，实际一引入 Mapper 就炸。后来把「必须真实启动 + 打健康接口」写成了每个里程碑的验收项。

**修法**：升级 MyBatis-Plus 到 3.5.17。

### 2. Jackson 2 与 Jackson 3 并存，误用会静默失败

**现象**：工具返回 `{"error":"结果序列化失败"}`，但日志里看不到异常。

**根因**：Spring Boot 4 和 Spring AI 2 都用 **Jackson 3**（`tools.jackson.*`），而项目里还留着 Jackson 2 的依赖。我写了 `new ObjectMapper()`（Jackson 2），它**没有注册 java.time 支持**，序列化带 `LocalDateTime` 的对象直接抛异常——而异常被工具层的兜底 try/catch 吞掉了。

**为什么难查**：`JsonInclude` 这类注解**仍在** `com.fasterxml.jackson.annotation` 包下（Jackson 3 复用了 2.x 的注解构件），所以"看到 com.fasterxml 的包名"会误导你以为在用 Jackson 2。

**教训（面试点）**：兜底 catch 要打得出来日志。当时如果只是 `catch (Exception e) {}`，这个问题会一直查不到。

**修法**：移除 Jackson 2 依赖，统一用 `tools.jackson.*`。

### 3. Spring AI 2.0 的 OpenAI 客户端换成了官方 SDK

Ollama 用小模型时，原本想用「OpenAI 兼容端点」接入。但 Spring AI 2.0 的 OpenAI 客户端底层已换成官方 `openai-java` SDK，要指向 Ollama 得自己搭 `OpenAIClient`。改用官方的 Ollama starter 更省事。

**顺带一个坑**：Ollama starter 默认也会注册一个 `EmbeddingModel`，和 DashScope 那个冲突。必须显式锁定 `spring.ai.model.embedding: openai`。

## 三、数据与领域类（jxj 真实库）

### 4. 逻辑删除配置会把 14 条在租记录全部过滤掉

**现象**：配了 MyBatis-Plus 的全局逻辑删除后，出租列表一条都查不出来。

**根因**：`jxb_chuzu`/`jxb_qiuzu` 的**活动行 `del_flag` 是空串或 NULL**，只有被删除的行才是 `'1'`。而全局逻辑删除会补 `del_flag = '0'`，一条都匹配不上。

**教训（面试点）**：**别假设历史库的字段语义跟框架默认一致**。RuoYi 这套老系统里，各表的 `del_flag` 含义并不统一。

**修法**：去掉全局逻辑删除配置，改由 `BizFilters` 显式写明每张表的可见性条件（判据是"不等于 `'1'`"而非"等于 `'0'`"）。

### 5. 72 台设备里只有 23 台对用户可见

**现象**：设备查询把库里 72 行全查出来了，其中大量是 `status`/`price` 全空的脏数据。

**根因**：平台的可见性口径是 `shelves_status = 1`（上架），另外 49 行是 `type=0` 的目录行。这个口径写在 RuoYi 的 mapper XML 里，**看表结构推不出来**。

**修法**：所有可见性条件收口到 `BizFilters`，照抄原系统的判据。

### 6. 品牌字段是个陷阱

`jxb_equipment.brand_id` 指向 `pms_brand`，但**库里的数据跟设备名对不上**（名字是"日立ZX200-3挖掘机"的车，`brand_id` 却指向三一重工）。真正可信的是 `second_cate_id`（指向 `sys_category` 的二级分类）。

**教训**：**同一个业务概念有多个字段时，要确认哪个是真的在用**。判断依据是看原系统的查询代码，不是看列注释。

## 四、框架用法类（LangGraph4j）

### 7. 并行扇出没有公开 API

**现象**：想搭"多个 Agent 并行跑完再汇总"的图，翻遍 `StateGraph` 只找到 `addEdge(String, String)`，没有任何多源汇合的重载。

**怎么查的**：反编译 jar 读字节码，确认——没有 `addEdge(List, String)`、没有 join/barrier、`Command.gotoNode` 是单个 String。

**真相**：并行是**隐式**的。给同一个源节点挂多条出边，编译期自动生成一个合成并行节点 `__PARALLEL__(源id)`；**所有分支必须汇合到同一个后继**，否则 `compile()` 直接抛错。

**另一个坑**：`ParallelNode` 是 public 的，但它由编译器生成，**不该自己 new**（我最初的方案就是自己构造，是错的）。

**修法**：
```java
g.addEdge(START, "A");  g.addEdge("A", "synthesize");
g.addEdge(START, "B");  g.addEdge("B", "synthesize");  // 同一个后继
```

### 8. 并行分支里抛异常会让整轮失败

**根因**：LangGraph4j 的并行节点内部用 `allOfFailFast` 等所有分支。

**教训（面试点）**：**并行分支必须自己吞异常**。一个域查不到不该拖垮其它域。这是"并行执行"容易被忽略的一环——串行时一个失败只影响后续，并行时会全灭。

### 9. 并行写同一个 key 会互相覆盖

**现象**：跨域综合时，三个域的结果只剩最后一个。

**根因**：LangGraph4j 的普通 channel 是"后写覆盖先写"。

**修法**：改用 `Channels.appender(ArrayList::new)`，把每次写入追加进同一个 List。

### 10. 构图必须显式给状态序列化器

`ReactAgentBuilder` 不给 `stateSerializer` 时，构图直接抛 `NullPointerException: stateSerializer is required!`。而且要用 Spring AI 专用的 `SpringAIJacksonStateSerializer`——通用的 Jackson 序列化器处理不了消息对象里的多态字段。

## 五、模型行为类（最值得讲的部分）

### 11. 本地小模型冷启动导致分类静默降级 ⭐

**现象**：同一个问题"小松200-8空调故障怎么解决"，一次判对、一次判成"未知"。

**怎么发现的**：审计日志里只记了路由结论，看不到分类依据。**先补上"记下分类器的原始判定"，再重跑**，才发现日志里两次都是 `TimeoutException`。

**根因**：模型调用统一设了 8 秒超时。但——
- Ollama 首次调用要把几 GB 权重读进内存（冷启动十几秒很正常）
- 主模型 MIMO 是**推理型**，会先"想"一段再输出

两层双双超时 → 这句话被判成 UNKNOWN → **静默降级到兜底 Agent**。用户只觉得"答得敷衍"，从现象上根本看不出是超时。

**教训（面试点，很适合主动讲）**：
1. **静默降级比报错更危险**——功能看起来"能用"，只是质量差，没人会发现
2. **超时要按层设置**：本地模型冷启动、推理型模型的思考时间，都不是一个固定值能覆盖的
3. **可观测性要先做**——不先把"判定依据"记进审计，这个 bug 根本查不出来

**修法**：按层设超时（小模型 30s / 主模型 45s / 生成 60s），并加启动后异步预热本地模型。

### 12. 推理型模型会把 token 全花在"思考"上

`mimo-v2.5` 是推理模型，响应里有 `reasoning_content`。实测一句 "Reply with exactly: OK" 配 `max_tokens: 20`，19 个 token 全用在推理上，**`content` 返回空字符串且不报错**。

**教训**：给推理模型设 `max_tokens` 要留足余量；解析响应时不能假设"有 choices 就一定有内容"。

### 13. 大模型会编平台规则（所以必须有证据闸）

问"在平台租设备的流程和押金怎么算"，知识库里没有相关内容时，大模型的反应**不是**说"我不知道"，而是凭对同类电商平台的印象编出押金比例、手续费率、退款时限——**编得像模像样，用户没法分辨**。

**修法**：证据闸在生成**之前**判断资料够不够；不够就不让它开口。注意闸必须在生成前——生成完再撤回，错话已经发出去了。

补充一层保险：生成后再让本地小模型核对"答案是否完全基于资料"。

### 14. 小模型对错误答案也给高分

qwen2.5:7b 直连测试时，把"小松200-8空调故障怎么解决"判成 `EQUIPMENT_QUERY`（设备买卖），置信度 0.8。

**教训**：**模型自报的置信度不能全信**。所以每层除了置信度阈值，还额外要求"意图不能是 UNKNOWN"，而且小模型的门槛（0.6）设得比大模型（0.4）高——小模型更容易自信地答错。

## 六、设计与算法类

### 15. 跨域问题被单 Agent 静默吃掉 ⭐

**现象**：用户问"有没有20吨挖机、附近能租吗、流程是啥"，只答了其中一部分。

**根因**：跨域意图被丢进了单 Agent 匹配，而规则是"能力交集最多者胜"。`CROSS_DOMAIN` 声明了 5 个能力，RentalAgent 交集 3 个、EquipmentAgent 只 1 个 → **整条交给租赁 Agent**，而它手里根本没有设备、资讯工具。

**特别值得讲的一点**：`ai_agent.priority`（设备 100 > 租赁 90）在这条路径上**根本没参与比较**——因为先比交集个数，平手才看优先级。**配置项写了不等于会生效**。

**修法**：跨域走独立的综合子图，不经过单 Agent 匹配。

### 16. 两个高权重词必然同分 → 歧义判不出来

所有高权重关键词都是 0.9 分。所以"二手设备出租"会同时命中设备(0.9)和出租(0.9)，**必然同分**，而单意图定案要求"严格高于第二名"，于是永远判不出来。

**这个特性有两个后果**：
- 它是跨域判定必须排在单意图定案**之前**的原因——单域那条路对"一次命中多个域"的输入天然无解
- 反过来，它也是个保护：不确定就不硬猜，下沉给模型

### 17. RRF 融合而不是加权求和

BM25 的分数**无上界**（几分到几十分），向量相似度是 0~1。直接加权求和的话，BM25 会完全盖住向量那一路。

RRF 只用"名次"不用"分数"：某条结果在任一路排第 r 名就得 `1/(k+r)` 分。不需要归一化，也不怕两路量纲不同。

### 18. 证据闸里有一段永远走不到的分支

**现象**：写测试时发现某个分支怎么都触发不了。

**根因**：原实现先判"达标条数够不够"、再判"最高分够不够"。但达标条数 ≥1 就意味着最高分必然达标——**第二个判断在第一关放行后永远不可能触发**。

**教训（面试点）**：**死分支不是无害的**，它会让读代码的人以为"这个情况被覆盖了"。写测试时发现"这个 case 构造不出来"，往往就是代码有问题，而不是测试写得不对。

**修法**：两个判据各管一件事——先排除"压根没有相关资料"，再排除"只有一条勉强沾边"（后者要 `min-evidence-count > 1` 才有实际约束）。

### 19. 发布意图被领域词抢走（评估发现的）

**现象**：评估集里"帮我发布一台出租"被判成"出租查询"。

**根因**：发布意图的高权重词写的是整串"帮我发布出租"，用户中间插个"一台"就匹配不上；而"出租"是出租查询的高权重词，命中 0.9 且无对手 → 关键词层直出。

**修法**：引入**动作意图优先**——发布是"动作"不是"查询"，命中高权重词就直接定案，且不参与跨域判定（否则"发布+出租"会被当成两个域）。

**效果**：准确率 92.3% → **96.2%**。

### 20. 关键词设计要避开"领域名词"

最初的设备意图高权重词里放了"挖掘机""装载机"。问题是这些机型名词在**出租、求租、需求**里都会出现，结果"附近有挖掘机出租吗"会被误判成设备查询。

**修正原则**：高权重词只放**几乎唯一指向该意图**的词（"求租""转人工"）；领域名词一律不放。

## 七、工程实践类

### 21. 测试账号删不干净

**现象**：跑了几轮测试后，`ai_user` 表里积了 130 行垃圾数据。

**根因**：测试清理用了 MyBatis-Plus 的 `deleteById`，而它走的是 `@TableLogic` **逻辑删除**——只把 `del_flag` 置成 `'2'`，行还留在表里。

**修法**：改用 `JdbcTemplate` 物理删除。

### 22. MockMvc 在 Spring Boot 4.1 里没有自动配置

`@AutoConfigureMockMvc` 在 Boot 4.1 的依赖里根本不存在（该自动配置未随 4.x 发布）。改为从 `WebApplicationContext` 手工构建：

```java
MockMvcBuilders.webAppContextSetup(webApplicationContext).build();
```

效果等价——DispatcherServlet 的拦截器照样执行，鉴权能被真实验证到。

### 23. 循环依赖：配置类 → 拦截器 → 服务 → 配置类

`WebConfig`（持有拦截器）→ `AuthInterceptor` → `AuthService` → 需要 `BCryptPasswordEncoder` 这个 Bean，而它定义在 `WebConfig` 里，形成环。

**修法**：把密码编码器拆到独立的 `PasswordConfig`；同时让拦截器只依赖 `TokenStore`（它本来就只需要解析令牌，不需要整个 AuthService）。

### 24. 启动时的日志刷屏

MyBatis-Plus 的 `StdOutImpl` 会把每条 SQL 的**完整结果集**打出来——启动时载入 3869 条区划 + 438 条字典就是几千行。

**修法**：去掉 `log-impl`，需要时用 `logging.level.<mapper包>: debug` 临时打开。

### 25. 自评误杀正确答案 ⭐（提示词反向暗示）

**现象**：问"平台收多少手续费"，知识库里明明有"平台收取多少服务费"这条（相关度 0.80，证据闸放行了），生成的回答也**完全正确**（3% / 5% / 5000 元上限，每个数字都能在语料里找到），但被自评判为不合格、改成"请转人工"。

**根因**：自评提示词里写的是——

> 如果回答里出现了资料中没有的具体数字、比例、时限、条款，判为"否"。

本意是让它核对数字，**实际效果是暗示它"看到数字就判否"**。7B 的小模型对这类暗示很敏感，看到回答里一串百分比就直接给了"否"，没去资料里核对。

**为什么难发现**：这个 bug 的表现是"用户明明能拿到答案，却被拒答"，从用户侧看就是"这机器人什么都不会"。而日志里只留一句"自评未通过"，**不记模型到底说了什么**，根本查不出是误杀还是真拦。

**修法**：
1. 提示词改成"逐条核对 + 给正例"——先去找依据，而不是先怀疑；
2. **把模型的原始判定打进日志**，误杀才能被发现。

**教训（面试点）**：提示词里的否定句要小心——**"如果出现 X 就判否"会把模型的注意力引到 X 上**，而不是让它去验证。防幻觉的提示词尤其容易写成这样。

### 26. 测试数据泄漏：同一个坑踩了两次

**现象**：知识库里多出 8 条 `test-*` 的测试数据没清掉。

**根因**：测试清理用了 `docMapper.deleteById`，而它走 `@TableLogic` **逻辑删除**——只把 `del_flag` 置成 `'2'`，行还在表里；而清理时的查询会自动过滤掉这些行，**下一轮就再也看不见它们了**。

**这个坑在 `ai_user` 上已经踩过一次并修了**（见第 21 条，属工程实践类），知识库这边忘了同步。教训是：**修完一个坑要顺带搜一遍同类代码**，而不是只修眼前那一处。

**修法**：改用 `JdbcTemplate` 物理删除，并额外清理孤儿切片。

**同一个地方又栽了第三次（顺序写反）**：修完物理删除之后，ES 里**还是**在积测试数据——
跑几轮就多出十几条 `[测试]` 文档，而且真的会被检索到、挤掉正确答案。

**根因**：`@AfterEach` 里写成了

```java
jdbcTemplate.update("DELETE FROM ai_knowledge_doc WHERE ...");   // ① 先删了 MySQL
List<AiKnowledgeDoc> docs = docMapper.selectList(...);           // ② 再查——已经查不到了
for (AiKnowledgeDoc doc : docs) { es.deleteByQuery(...); }       // ③ 循环体一次都没执行
```

先删了数据源，再回头去数据源里查 id 来删索引——**②永远返回空，③是个死循环**。
而且它**不报错、不告警**，只是悄悄什么都不做。

**修法**：顺序倒过来（先查、后删），删 ES 时显式 `refresh`，
最后再跑一次 `reconcileIndex()` 对账兜底——对账走的是线上同一套逻辑，
比再补一个 `sleep` 靠谱。

**教训（很值得讲）**：这是一个**"清理代码自己坏了但没人发现"**的例子。
清理逻辑和业务逻辑不一样，它坏了不会有任何现象，只会让脏数据慢慢积累，
等到"检索结果莫名其妙变差"的时候，已经查不出是哪来的了。
所以清理逻辑也要有**可验证的收敛判据**——这里是"跑完测试套件后索引文档数应当不变"，
比"看起来清干净了"可靠得多。

### 27. ES 索引被自动创建，映射是错的

**现象**：删掉索引后没重启应用，直接触发入库——ES **自动创建了同名索引**，但用的是默认映射。

**根因**：ES 默认允许写入时自动建索引。自动建出来的索引**没有 IK 分词、没有向量字段**，此时检索会静默退化成"什么都搜不到"。

**教训**：**搜索引擎的索引结构必须由应用显式管理**。要么关掉自动创建，要么保证任何写入前索引已按正确映射建好。这次是靠人工发现，更好的做法是在写入前先 `ensureIndex()`。

### 28. 别用 `taskkill /IM java.exe`

调试时为了杀掉占用端口的旧实例，我用 `taskkill /F /IM java.exe` 把**所有** Java 进程都杀了——包括同时跑着的 Elasticsearch。结果 ES 被误杀，要重启一遍（冷启动又要等几十秒）。

**教训**：按 PID 精确杀，别按进程名批量杀，尤其是本机同时跑着多个 Java 服务（ES、应用、可能的 Milvus 等）的时候。

### 29. 证据闸阈值形同虚设——因为判据本身选错了 ⭐

**现象**：知识库有内容之后，一个**完全不相关**的问题（"平台的火箭发射服务怎么预约"）
向量相关度能拿到 **0.7655**，远超 `min-retrieval-score` 默认的 0.6，**证据闸直接放行**。
真正把它拦下来的是第二道自评——而自评时灵时不灵。用户侧看到的就是"这机器人一半概率在编"。

**怎么发现的**：这个是**被测出来的**，不是被看出来的。写 `M6KnowledgeTest` 时
那条"知识库里没有的内容必须拒绝作答"的用例稳定失败，才发现闸根本没起作用。
当时的第一反应是"阈值调高一点"，但调高的过程中发现不对劲——调多高都不对劲。

**根因不是阈值，是判据。** 标了 34 条样本（24 条有答案 + 10 条没答案）画曲线才看清：

| 判据 | 有答案（中位） | 无答案（中位/最高） | 零漏放分界 | 该分界误拦率 |
|---|---|---|---|---|
| 向量最高相似度 | 0.829 | 0.757 / 0.829 | 0.830 | 54% |
| 精排分（只喂正文） | 0.379 | 0.158 / 0.183 | 0.184 | 29% |
| 精排分（喂标题+正文） | **0.837** | 0.130 / 0.190 | **0.191** | **13%** |

**向量相似度这两类的区间几乎完全重叠**——阈值取 0.6 时误拦 0%、漏放 100%；
取到 0.83 才不漏放，但那时 54% 能答的问题也被拒了。**根本没有可用的分界点。**

为什么向量相似度这么不中用：它是**双塔**——问题向量和资料向量各自独立算好再比，
两者之间没有交互。所以它对"两个向量恰好在同一片区域"敏感，
对"资料里到底有没有回答这个问题"不敏感。语料一多，所有问题的 top1 都落在同一段高分区间里。

**修法**：换成**交叉编码器精排**——把问题和资料**拼在一起**过模型，输出相关性分。
它对"这条资料能不能回答这个问题"是直接建模的，区分度完全不同（见上表）。
链路改成 `混合召回收窄候选 → 精排给候选打分 → 证据闸按精排分判定`，
阈值取 0.19（零漏放点）。

**效果**：漏放率 **100% → 0%**，误拦率 **0% → 13%**。
这个取舍是刻意的：误拦只是多转一次人工，漏放是直接给用户一个编造的答案。

**顺带发现的一个值钱细节：喂给精排的必须是「标题 + 正文」。**

第一版只把正文喂给精排，误拦率停在 29% 下不来。查下来发现一个反直觉的现象：
问"押金怎么退"，对着**正文**精排只有 **0.18**；而把语料里那条的**标题**
（"租设备要交押金吗，押金怎么退"）当问题去精排，能拿 **0.79**。

原因是知识库的**标题本身就是问句形态**（"押金怎么退""哪些设备不能发布"），
和用户提问方式天然对得上；而正文是陈述式的解答，往往一次都不重复问题里的说法。
只看正文，精排没法确认"这条到底在不在回答这个问题"。加上标题之后误拦率 29% → 13%。

**这个细节的另一层意义是一致性**：生成回答时喂给模型的就是"【标题】+ 正文"，
证据闸判的应当和模型看到的是同一份材料，否则会出现"闸照着正文判、模型照着标题答"的错位。
（顺带一提，这也是为什么校准脚本要直接调用实现里那个拼接方法——评估必须测实现真正用的东西。）

**教训（很好的面试素材）**：

1. **指标不work的时候，先怀疑判据，别急着调参数。** "把阈值从 0.6 调到 0.8"是错的努力方向——
   它在一个根本没有区分度的维度上找分界点。**先证明这个维度可分，再谈阈值。**
2. **画曲线比拍数字强的地方**，不是"选得更准"，而是**能看出"选不出来"**。
   如果只是拍个 0.75，这个问题会一直藏着。
3. **"双塔召回"的分数不适合当绝对判据。** 它的用途是**排序**（把相关的排前面），
   不是**判定**（这条到底相不相关）。同样的坑在别的 RAG 系统里也很常见。
4. **代价要显式说出来**：13% 的误拦率不理想，但它是有意识的选择，
   不是"调不出来算了"。面试时讲清楚取舍，比讲一个漂亮的假数字好。

## 七之二、M9 知识库上传踩的坑

### 30. 命令行工具输出正确结果却返回非 0 退出码 ⭐

**现象**：接入 LiteParse（`lit` CLI）后，**所有 PDF 上传都报"文档解析失败（退出码 1）"**，
但手动在终端里跑同一条命令却完全正常。

**怎么发现的**：写了个最小 Java 程序把 `ProcessBuilder` 跑一遍，把退出码、stdout 字节数、
stderr 一起打出来：

```
cmd=lit         启动异常: IOException（无扩展名的 sh 脚本，Windows 跑不起来）
cmd=lit.cmd     exit=1 stdout=13860B stderr=(空)   ← 明明有完整输出
```

**根因**：`lit` **会在正常输出结果的同时返回非 0 退出码**——它内部会尝试给页面做
Tesseract OCR，而语言包要从 GitHub 下载（本机到不了），那个失败把退出码带成了 1。
这个失败跟我们无关（我们本来就传了 `--no-ocr`），但它污染了退出码。

**修法**：判据从"退出码是不是 0"改成"**有没有拿到输出**"——
有输出就继续用，只在输出为空时才当失败。顺带记下 exit code 供排查。

**教训（很好的面试素材）**：
1. **外部进程的退出码不是可靠的成功信号**，尤其是不受你控制的开源 CLI。
   要按"产物是否符合预期"判断，而不是按它自报的状态。
2. **这个 bug 的现象和根因隔得很远**：表面是"解析失败"，实际是"OCR 下载语言包失败"。
   把退出码、stdout、stderr 三个都打出来，才一眼看穿。

### 31. 声明了超时配置却没接到客户端上

**现象**：给扫描件做多模态 OCR，21 页里 **14 页返回空**，另外 7 页正常。
日志里是 `ReadTimeoutException`。

**根因**：我在类里写了 `@Value("${rag.parse.ocr.timeout-ms:60000}") private long timeoutMs;`，
**但压根没把它设置到 RestClient 上**——用的是框架默认超时。
而 200 DPI 的 A4 整页转 base64 有好几 MB，上传加推理根本来不及。

**教训**：**配置项声明了不等于生效**（和踩坑记录第 15 条"`ai_agent.priority` 配了也没用"
是同一类问题）。更阴的是它不报错、不警告，只是默默用了另一个值。
修法是在构建客户端时显式设 connect/read 超时。

**现象为什么会误导人**：表现是"OCR 莫名其妙没识别出内容"，
第一反应会怀疑"是不是模型不行/图片质量差"，而真实原因是超时。

### 32. 跨页表格合并判据被页眉页脚废掉了 ⭐

**现象**：实现了跨页表格合并，但在一份 31 页的国标 PDF 上**一次都没触发**——
明明有两页的表格标题都写着"表4 检验项目（**续**）"，是铁证如山的续表。

**根因**：判据是"表格必须紧贴页面首/尾"（上一页以表格结尾 + 下一页以表格开头）。
但**国标、论文这类文档每页都有页眉和页脚页码**——表格永远不可能是页面的第一行或最后一行。

**修法**：允许页面首/尾有**少量**非空行（`EDGE_TOLERANCE_LINES = 2`），
把页眉页脚容忍掉。抽成纯函数 + 合成用例单测（构造带页眉页脚的续页），
这类版面问题在真实文档上很难稳定复现，必须能单测。

**另一个更隐蔽的 bug 出现在同一段代码里**：判断"上一页是否以表格结尾"时，
我传进去的是**当前页的行数组**和**上一页的表格块**——行号根本对不上。
两处都修了才对。

**教训**：版面启发式的判据要**按真实文档的形态去设计**，
不能假设"表格就在页首/页尾"。而且这类逻辑务必抽成纯函数单测——
靠真实 PDF 验证一次要跑 6 分钟还花钱。

### 33. 公式被版面算法误判成表格

**现象**：国标 PDF 里的**公式**被识别成了 markdown 表格：

```
| Ein回转 =∑ i=1∫ n | t2 Uin回转 Iin回转dt t1 | ………………(1) |
|---|---|---|
| Eout回转 =∑ i=1∫ n | ... | ………………(2) |
```

它有表头行、有合法的 `|---|---|` 分隔行、列数也一致——**格式上完全合法**。
照单全收的话，知识库里一半的"表格"会是公式。

**修法**：加三条校验（都在 `MarkdownTableExtractor`）：数据行数 ≥ 2、
单元格不能过长、表头不能像公式（含 `=`/`∑`/`∫` 或以编号结尾）。
其中"数据行数 ≥ 2"最有效——那类假表格无一例外只有 1 行数据。

**教训**：解析器输出的"结构化结果"**必须校验**，不能因为它声称是表格就信。
校验规则要从**实际的坏样本**里总结，不是凭空想。

### 34. Windows 下 mysql 客户端会把 UTF-8 的 SQL 脚本读成 GBK

**现象**：执行建表脚本后，表结构正常，但**所有中文注释都变成了乱码**
（`知识库表格` 变成 `鐭ヨ瘑搴撹〃鏍硷`——典型的 UTF-8 字节被当 GBK 解读后再存成 UTF-8）。

**根因**：Windows 控制台的 `mysql` 客户端默认字符集不是 UTF-8，读脚本文件时按 GBK 解。

**修法**：导入时显式指定：

```bash
mysql --default-character-set=utf8mb4 -uroot -p jxj < src/main/resources/db/migration/V2__knowledge_table.sql
```

**教训**：这个坑**不影响功能**（表名、列名是 ASCII 所以没事），只脏了注释，
所以很容易被忽略、一直留在库里。凡是往数据库灌中文，先确认客户端字符集。

## 八、知识库语料说明

库里原本只有 13 篇文章，**其中 9 篇正文只有图片**，剩下 4 篇的正文长度是 10、38、13、8 个字——等于没有内容。用它演示"问规则"是演示不出来的：证据闸永远拦下，看起来像功能坏了。

> ⚠️ 这是**演示用示例语料，不是平台真实政策**。真实上线要替换为运营确认过的正式文本。

这样系统的开箱表现才正常：能答的答，答不了的老实说不知道并转人工。

## 九、面试时怎么组织这些内容

### 如果只让你讲三个

1. **证据闸判据选错**（第 29 条）——体现你会用数据判断"这个方向对不对"，
   而不是调参数调到满意为止；而且知道**双塔相似度适合排序、不适合判定**这个本质
2. **静默降级**（第 11 条）——体现你会做可观测性、知道"能跑"和"跑得好"的区别
3. **自评误杀**（第 25 条）——体现你懂提示词的细节陷阱，且知道"防幻觉"本身也会出错

**第 15 条（跨域被单 Agent 吃掉）**也是好素材：体现你会查"为什么配置没生效"，
而不是只看配置写没写。**第 13 条（大模型会编平台规则）**则是证据闸存在的理由本身。

### 高频追问及准备

**Q：怎么保证 AI 不乱答？**
三层：证据闸（生成前，资料不够不让开口）→ 提示词硬约束（规则类问题不许凭常识答）→ 生成后自评（核对是否完全基于资料）。另加数据飞轮收集答不上来的问题，人工补库。

**Q：多 Agent 怎么选？**
显式映射，不是猜：意图 → 能力 → Agent 对照表 + 优先级 + 角色权限。跨域时按"命中域数 ≥2"走综合子图。

**Q：成本怎么控制？**
三层意图识别，62% 关键词直出（零成本）、35% 本地小模型（免费）、只有 4% 走到云端大模型。会话粘性让追问不重复分类。

**Q：失败了怎么办？**
分层降级而不是重试：小模型超时 → 大模型；大模型也不行 → 兜底 Agent；检索失败 → 证据闸拦下并转人工。目前**没有**自动重试——因为模型调用超时后重试可能造成重复计费，且对话场景下用户更在意响应速度。
