## 一、项目是什么

**机械家**是一个二手工程机械交易平台（真实业务库 `jxj`，159 个 Java 类、约 1.5 万行）。
这个项目给平台做一个 **AI 客服 / 导购 Agent**：用户可以用自然语言找设备、找出租、找活、
问平台规则，也能让助手代他发布出租或求租信息，答不上来的转人工。

**它不是"套壳聊天"**——有几条硬约束贯穿始终：

| 约束 | 为什么 |
|---|---|
| 规则类问题**资料不足就不许开口** | 大模型会编平台规则（编得全套、报得出费率），客服场景里这是事故 |
| 写操作**必须确定性** | 发布要落库，模型抽错字段会被校验拦下重填，绝不写半截数据 |
| **98% 的请求不产生云端费用** | 平台客服是高频场景，每句话都调大模型不现实 |
| 路由结论**可解释、可审计** | 要能回答"这句话为什么交给了这个 Agent" |

## 二、整体架构与设计思路

### 2.1 三种编排范式，按"谁来决定走向"分工

这是整个项目最核心的一条设计判断：**不是所有流程都该让模型决定**。

| 编排方式 | 用在哪 | 谁决定走向 |
|---|---|---|
| **ReAct 图**（LangGraph4j `ReactAgent`） | 每个业务 Agent 内部 | **模型**决定调什么工具、几步 |
| **并行扇出图**（`CompositeGraph`） | 跨域问题综合 | 代码决定扇出，各域 Agent 内部仍是 ReAct |
| **确定性状态机**（纯 Java） | 发布工作流 | **完全由代码决定**，模型只负责抽字段 |

**为什么发布不用图**：发布是**写操作**且**线性**，还带外部状态（草稿、确认令牌）。
写成状态机比画图清楚，而且"模型不能决定流程"这条约束在代码层面就是硬性的。

**为什么跨域用图**：跨域是"一句话里问了多个领域"，天然可并行——各域互不依赖，
并行跑完再汇总。用图表达扇出 + 汇合最自然。

### 2.2 分层

```
com.jixiejia.agent
├── api/          接口层（聊天 / SSE / 鉴权 / 管理接口）
├── auth/         登录、令牌、角色、登录拦截器
├── router/       路由链：7 步 + 会话粘性 + 指代消解 + Agent 注册表 + 审计
├── classify/     三层意图分类（关键词 → Ollama 小模型 → MIMO 大模型）
├── agent/        5 个业务 Agent（ReAct）+ AgentContext / AgentExecutor
├── tool/         7 个 @Tool 查询工具 + 能力注册表 + 角色白名单
├── graph/        跨域综合子图（LangGraph4j 并行扇出）
├── publish/      发布工作流（表单 → 确认令牌 → 落库待审核）
├── rag/          知识入库、混合召回、精排、证据闸、自评、飞轮
│   └── parse/    文档解析：LiteParse CLI + 多模态 OCR + 表格结构化（跨页合并）
├── llm/          模型客户端、分层的超时封装、提示词库、小模型预热
└── persistence/  jxj 业务表（**只读**）+ ai_* 表（可读写，17 张）
```

**两个刻意的隔离**：
- **只读 Mapper 与写入 Mapper 分包**——查询是运行时拼条件的（易脏数据），
  写入只在确定性路径上，混在一起就失去隔离意义
- **提示词放 `.md` 文件不放数据库**——数据库方案会丢掉 code review、git 回滚、
  环境一致性；而提示词里有防幻觉护栏，被随手改掉会出事

### 2.3 五个 Agent

| Agent | 职责 | 能力 |
|---|---|---|
| EquipmentAgent | 设备买卖查询 | `equipment` |
| RentalAgent | 出租查询 + 求租查询 | `chuzu` / `qiuzu` |
| KnowledgeAgent | 平台规则 + 行业资讯 | `policy` / `news` |
| PublishAgent | 发布出租 / 求租 | `publish` |
| GeneralAgent（兜底） | 闲聊、认不出的话 | **不挂任何工具** |

> **兜底 Agent 为什么刻意不挂工具**：它一旦能查数据，就会在路由出错时给出
> "看似可信其实串了领域"的答案，**掩盖真问题**。宁可让它老实说"我帮不上忙"。

## 三、一条消息的完整数据流

这是面试里最容易被追问的部分，建议照着讲一遍。

```
用户：「有没有20吨挖机、附近能租吗、流程是啥」
  │
  ▼ POST /api/chat（带 Bearer 令牌）
① 身份检查 ——— 必须登录，否则 401
  │
  ▼
② 系统命令 ——— 命中 /reset 就地短路
  │
  ▼
③ 跨域判定 ——— 命中 ≥2 个不同领域？
  │        ├─ 是 → 【跨域综合子图】
  │        │        START ─┬─ EquipmentAgent ─┐
  │        │               ├─ RentalAgent    ─┼─→ synthesize → END
  │        │               └─ KnowledgeAgent ─┘
  │        │        各域并行跑完，汇总成一条回答
  │        │
  │        └─ 否 ↓
  │   关键词扫描 ——— 命中且与粘性一致 → 沿用（不调模型）
  │        │        命中但话题变了   → 立刻切换
  │        │        没命中 + 含指代词 → 沿用粘性（"那这个呢"）
  │        │        没命中 + 不含指代词 → 往下走
  ▼
④ 指代消解 ——— 只有真要叫模型时才做（用最近 5 轮把"那台"改写成完整问题）
  │
  ▼
⑤ 三层意图分类
  │    第 1 层 关键词加权   ← 零成本、毫秒级、可复现
  │    第 2 层 本地小模型   ← Ollama qwen2.5:7b，免费
  │    第 3 层 云端大模型   ← 只有前两层都不行时才用
  ▼
⑥ Agent 匹配 ——— 注册表 + 角色权限 + 优先级；拿到 Agent 和它的工具白名单
  │
  ▼
⑦ 执行 + 审计 ——— 落 ai_audit_log（含意图、置信度、命中层、路由阶段）
  │
  ▼
回答 + 溯源依据（sources）
```

**知识线是单独的第三条路**（不走 ReAct Agent）：

```
意图 = KNOWLEDGE_QUERY
  → 混合召回 20 条（BM25 + KNN，RRF 融合）
  → 精排打分（交叉编码器）
  → 证据闸：分不够就不生成，直接兜底 + 记飞轮
  → 回填本体（表格摘要→完整表格；命中块→同章节邻块）
  → 生成（模型标 [1][2] 引用序号）
  → 自评（本地小模型核对是否完全基于资料）
  → 答案 + sources（标题/章节路径/页码/片段）
```

**为什么知识线不用 Agent**：这条道的硬要求是"资料不足就不许答"，
而 ReAct Agent 里的模型有自主权——**完全可能不去查资料、直接凭印象回答**，那样证据闸就形同虚设。

## 四、技术亮点（简历上的那几条，展开讲）

### 亮点 1：用数据证明"判据选错了"，而不是调参数调到满意 ⭐⭐⭐

**问题**：一个完全不相关的问题（"平台的火箭发射服务怎么预约"）向量相关度拿到 **0.7655**，
远超阈值 0.6，证据闸直接放行。真正拦住它的是第二道自评——而自评时灵时不灵。

**第一反应是"阈值调高一点"**，但调高的过程中发现不对劲：调多高都不对劲。

**做法**：标了 **34 条样本**（24 条有答案 + 10 条没答案）**画阈值曲线**：

| 判据 | 有答案（中位） | 无答案（最高） | 零漏放分界 | 该分界误拦率 |
|---|---|---|---|---|
| 向量最高相似度 | 0.829 | 0.829 | 0.830 | **54%** |
| **精排分（喂标题+正文）** | **0.837** | 0.190 | **0.191** | **13%** |

**两类区间几乎完全重叠——根本不存在可用的分界点。**

> ⚠️ 上表是**当时（16 篇小语料）**的测量。换到真实语料（22 篇 / 233 个切片）之后，
> **向量那一行几乎没动**（0.828 / 0.829 / 0.830），**精排那一行整体右移**
> （有答案中位 **0.743**、无答案最高 **0.581**、零漏放分界 **0.582 / 误拦 42%**）。
> **"换判据"这个结论不变**，但线上阈值还停在 0.19——按新分布，**闸现在是漏的**。
> 详见亮点 8。

**根因不是阈值，是判据**：向量相似度是**双塔**（问题和资料各自算好再比，两者没有交互），
所以它对"两个向量恰好在同一片区域"敏感，对"资料里到底有没有回答这个问题"**不敏感**。
**适合排序，不适合判定。**

**修法**：换成**交叉编码器精排**（把问题和资料拼在一起过模型），
链路改成 `混合召回收窄候选 → 精排打分 → 证据闸按精排分判定`。

**数字：漏放率 100% → 0%**（误拦 0% → 13%，是刻意偏保守的取舍：
误拦只是多转一次人工，漏放是直接给用户一个编造的答案）。

> ⚠️ 这个 0% 是**在当时那份语料、那个阈值（0.19）下**成立的。语料换成真实规模后，
> 精排的零漏放分界右移到 **0.582**，而阈值没跟着调，**当前漏放率是 10%**。
> **判据选对了，阈值仍然要随语料重新校准**——这本身就是半条教训。

> **顺带一个值钱的细节**：喂给精排的必须是**「标题 + 正文」**。
> 知识库的**标题本身就是问句形态**（"押金怎么退"），和用户提问天然对得上；
> 而正文是陈述式的，往往一次都不重复问题里的说法。只喂正文时"押金怎么退"只能拿 0.18，
> 加上标题能到 0.79——**误拦率 29% → 13%**。

**面试怎么讲**：
1. **指标不 work 的时候，先怀疑判据，别急着调参数。** "把 0.6 调到 0.8"是错的努力方向——
   在一个根本没有区分度的维度上找分界点。
2. **画曲线比拍数字强的地方不是"选得更准"，而是能看出"选不出来"。**
   如果只是拍个 0.75，这个问题会一直藏着。
3. **双塔召回分数适合排序、不适合判定**——这个认识在别的 RAG 系统里同样成立。

### 亮点 2：融合排序 ≠ 相关性排序（RRF 的系统性偏置）⭐⭐

**问题**：用户问"挖掘机生命周期可能出现什么危险因素"。知识库里明明有一份
《矿用机械正铲式挖掘机 安全要求》，第 10-11 页就是「表 1 危险一览表」（32 行）。
但模型回答：

> "危险因素**列在表1中，但表1的具体内容没有在提供的资料里列出**。"

**模型自己指出了答案在哪，却看不到它。**

**排查（层层排除，值得复述）**：
```
1. 先怀疑自评误杀（项目里有前科）→ 关掉自评重跑，仍答不上来 → 排除
2. 打印检索命中 → 5 条全是正文段落，tableId 全为 null
3. 确认表格确实入库了（MySQL 有、ES 有、带 tableId）→ 排除入库问题
4. 直接查 ES 的 KNN   → 表格摘要排第 2 名（0.8351，第 1 名 0.8411）
5. 直接查 ES 的 BM25  → 表格摘要在前 10 名里根本没出现
6. 看融合逻辑         → 真相在这里
```

**根因**：RRF 的 `1/(k+名次)` 是**累加**的：

```
表格摘要     ：只在向量那路排第 2   → 1/(60+2)              = 0.0161
某个正文段落 ：BM25 第1 + 向量第5  → 1/(60+1) + 1/(60+5)   = 0.0318
```

**只走单路的资料，一定输给"两路都进前几名"的资料**——哪怕它在单路里排第 2。
表格摘要恰好如此：语义上最相关，但关键词路线几乎匹配不上
（"挖掘机生命周期可能出现什么危险因素"和表格里"序号|危险"的写法没有词面交集）。

**修法**：**召回放宽、精排收紧**。之前是「RRF 取前 5 → 精排这 5 条」，
等于让 RRF 替精排做了取舍；改成「**召回 20 条 → 精排排序 → 取前 5 条喂模型**」。

**效果**：同一个问题现在能完整列出 9 类机械危险，**其中好几条在摘要前 5 行之外**——
证明"命中摘要 → 取回完整表格"这条回填链路也一起跑通了。

**面试怎么讲**：**融合管"别漏"，精排管"挑准"，两件事不能合成一步。**
拿融合的前 K 直接当最终结果，就是让排序算法替相关性判断做决定。

### 亮点 3：父子块和表格，是同一个模式的两次应用 ⭐⭐

这是设计上的一个"顿悟"，能看出是否真的理解了自己在做的事：

```
        检索入口（向量化）        本体（不向量化，取回来用）
        ─────────────────       ─────────────────────
第一处：  子块                    父块
第二处：  表格摘要                表格本体
```

**为什么要拆成两半**：检索要的是**短而准**（长了向量表征就糊），
生成要的是**全而完整**（缺表头就会答错）。**短的负责被找到，长的负责被读懂。**

> ⚠️ 关键澄清：**"不向量化" ≠ "不存"。** 本体（表格 markdown、父块全文）
> 一律**结构化存进 MySQL**，靠 `tableId` / `section_path` 取回。
> 不存的话，回填时拿什么取？

**案例**：31 页的国标 PDF，表格跨页被切散。方案是——
表格本体存 `ai_knowledge_table`（完整 markdown，不切片、不向量化），
只把「文档标题 + 表格标题 + 表头 + 前 5 行 +（共 N 行）」当摘要向量化；
检索命中摘要 → 按 `tableId` 取回完整表格 → 喂模型。

**跨页合并用的是版面启发式**：第 N 页以表格结尾 + 第 N+1 页以同列数表格开头 → 接成一张。

> 这里踩了个坑：判据最初要求"表格必须紧贴页面首/尾"，
> 而**国标、论文这类文档每页都有页眉页脚**——表格永远不可能是页面第一行或最后一行。
> 结果真实的跨页续表（两页标题都写着"表4 检验项目（续）"）**一次都没合并成**。

### 亮点 4：三层意图识别 + 把"不确定"降级成"提示"而不是"结论" ⭐⭐

**成本结构**（63 条评估集实测）：

| 层 | 占比 | 成本 |
|---|---|---|
| 关键词加权 | 40% | **零成本、毫秒级、可复现** |
| 本地小模型（Ollama qwen2.5:7b） | 59% | **免费** |
| 云端大模型 | **2%** | 唯一有费用的部分 |

**98% 的请求不产生云端费用。**

**这套设计的演进本身就是亮点**——同一个错犯了三次：

| 次数 | 怎么错的 | 修法 | 教训 |
|---|---|---|---|
| 1（第 19 条） | "帮我发布一台出租" 被"出租"抢走判成出租查询 | 引入"动作意图优先" | 高权重词写整串会漏 |
| 2（第 20 条） | 机型名词当高权重词 → "附近有挖掘机出租吗"被判成设备查询 | 领域名词一律不进高权重词表 | 关键词要挑"几乎唯一指向"的 |
| 3（第 51 条） | "我想出租一台洋马60" 又被"出租"抢走 | **不再让关键词定案**，改成"认出发布意愿 → **当提示交给模型**" | **"用词表判定案"有天花板** |

**第 3 次的关键取舍**，也是这一条最值钱的地方：

> **提示是建议（模型能推翻），定案是结论（错了就是错的）。**
> 同一条判据，**当提示用是安全的，当判据用是危险的。**
> 不确定的时候，把它**降级成提示**——这比"删掉"更细的一档处理。

**而且"先补量尺再改代码"这个顺序救了一次**：原来的 26 条评估集里"发布"只有 1 条，
且恰好是词表专门为它写过的"帮我发布一台出租"——**改坏了也看不出来**。
扩到 63 条后，**同一套代码**的基线从 96.2% 掉到 87.3%——
**不是系统变差了，是原来的尺子量不出来。**

### 亮点 5：用户一句提问暴露的结构性缺陷——重复的意图在悄悄拉低准确率 ⭐

**用户看着"工地马上开工了还差两台挖机"问**："这不就是求租吗？"

查下去发现项目**自己内部就矛盾**：

| 位置 | 怎么说的 |
|---|---|
| `QiuzuQueryTool` | 求租 = "**要用机器的人正在找机器**" ← 对的 |
| `ToolCapability` | `/** 求租（机主找活） */` ← 反的 |
| `Intent.QIUZU_QUERY` | "用户是机主：手里有机器、想给机器找活干" ← 反的 |

**数据库站在工具那边**（`jxb_qiuzu` 的列是"工程类型/进场时间/工期/拖车费"，
装的就是"要租机器的人报的工程"）。同一个业务概念，三处描述，两个方向。

**根因**：平台把"求租"和"用机需求"建成了**两张表**，代码里对应地有了**两个意图**
和**两个工具**——而**业务上它们是同一件事**。两个几乎同义的选项摆在模型面前，
句子被判歪是必然的。

**修法**：删掉 `DEMAND_QUERY` 意图与 `demand` 能力；`search_qiuzu` 合并两张表
（返回里用 `source` 标出来源）；`search_xunjia`（有人想**买**新机）挪到设备买卖那侧。

**数字：准确率 95.2% → 96.8%（61/63）。删除一个重复意图，涨了 1.6 个百分点。**

> **这本身就是结论**：那个重复不是无害的冗余，它在持续制造误判。

**面试怎么讲**：
1. **用户凭直觉指出的问题，往往比指标更早暴露结构性缺陷。**
   评估集只说"这里有错判"，只有用户那句"这不就是求租吗"才让人看出：
   **问题不是判定不准，是分类体系里有个重复项。**
2. **同名不同义的描述，比没有描述更危险**——三处描述两个方向，它们从来没对齐过。
3. **删功能也能提升准确率。** 通常优化是"加"（加词、加规则、加模型），
   这次是**减**。遇到"怎么调都不准"的时候，该问一句：
   **"是不是分类本身就有两个一样的选项？"**

### 亮点 6：答案溯源闭环——从"说得清出处"到"看得到原件" ⭐

**需求是用户"用"出来的**：系统已经能说"依据来自《矿用机械正铲式挖掘机 安全要求》第 10 页"，
用户一句"**我想要前端回溯原始的 PDF 不行吗**"才暴露出：**说法和入口是两回事**。

**缺的是地基**：上传时 `file.getBytes()` 读进内存、解析完就丢，
文档表里**没有任何文件路径字段**——不是前端不行，是原件压根没留。

**做成了三级可验证**：答案里的 `[1]` 可点 → 跳到 PDF 第 N 页 → 看到原始表格。
**不是"我说得对"，是"你自己去看"。**

**其中几个值得讲的判断**：

| 判断 | 理由 |
|---|---|
| **"转 PDF"不是默认动作，是给 Office 补的例外** | 浏览器的能力边界：PDF/图片/纯文本都能直接显示，**只有 docx/xlsx/pptx 渲染不了**。判断依据是"浏览器能渲染什么"，不是"我们想支持什么" |
| **聊天页只预览、不给下载** | 知识库里有国标这类**有版权**的文档，也常混进内部资料 |
| **不暴露可直接访问的 URL** | 前端 fetch 带令牌取字节再喂渲染器——不产生可另存、可转发的直链 |
| **先转义、再替换角标** | 顺序不能反：知识库内容是**用户上传的文档**，里面完全可能有尖括号甚至 script 标签 |
| **越界编号降级成纯文本** | 宁可少一个角标，也不能让用户点开一份**错的原件**——那比没有链接更伤信任 |

**边界照实说**：角标只保证**编号合法**，不保证**标得对**（`[3]` 可能其实是 `[1]` 的内容）——
那要靠生成后的 **NLI 逐句校验**，**还没做**。

### 亮点 7：外部工具与环境带来的坑（体现工程素养）

这几条不属于算法，但很能体现"踩过真坑"：

| 坑 | 教训 |
|---|---|
| **命令行工具输出正确结果却返回非 0 退出码**（LiteParse 内置 OCR 下载语言包失败污染了退出码） | **外部进程的退出码不是可靠的成功信号**，要按"产物是否符合预期"判断 |
| **声明了超时配置却没接到客户端上** | **配置项声明了 ≠ 生效**（同一类问题在 `ai_agent.priority` 上又犯过一次） |
| **embedding 批量上限 16 > 接口上限 10，潜伏很久** | **"一直没出问题" ≠ "没问题"**——正确性依赖"历史上没出现过大于 10 个切片的数据"这个隐含假设 |
| **扫描页 OCR 串行，15 页跑十几分钟** | **"慢"和"挂"在用户眼里是一回事**；独立任务就该并发（并发 4 后 **83 秒**） |
| **兜底分支返回不可变 `List.of()`，`set()` 抛异常** | **"兜底路径"要单独问一句"它真的兜住了吗"**——传一张单页扫描的 PDF 必失败 |
| **扩展名里能带路径**（`extensionOf` 返回最后一个点之后的全部内容） | **安全校验要问"写路径设防了吗"**；**白名单比黑名单可靠** |

### 亮点 8：指标本身也会失真——口径、语料、一个认识没用到所有地方 ⭐⭐⭐

**问题**：文档里写着"检索 Recall@5 混合 **95.8%**"，用户看了一眼说：

> "这个准确率太夸张了，我感觉不太可能。"

**结论：他是对的。** 而且这件事暴露的不是一个数字，是**三层问题**。

**① 数字过期了，而且不会自己报警。**
复跑只有 **87.5%**。查时间线：评估脚本是当天 **12:04** 提交的，两本国标是 **17:25** 才上传的。
**95.8% 测于 16 篇 FAQ 小语料——语料变了，数字没跟着变。**
**能复跑 ≠ 会复跑**：脚本一直在仓库里躺着，但没有任何机制提醒你该再跑一次。

**② 口径量错了段。**
评估调的是 `retrieve(q, 5)`，**只到 RRF 融合层**；
线上是 `retrieve(q, 20)` → 精排 → 取 5。补上流水线口径后：

| 口径 | Recall@5 |
|---|---|
| 混合（融合层取 5） | 87.5%（21/24） |
| **线上流水线**（召回 20 → 精排 → 取 5） | **83.3%（20/24）** |

**流水线比融合层还低**——精排在这一批上净损失了一条。
同样是"Recall@5"，两个口径**差 4.2 个点**。**没有写清口径的指标，等于没有指标。**

**③ 一个认识用在一处，不等于用在了所有该用的地方。**
顺着漏检清单，看到最刺眼的一条：「设备验收有问题怎么办」**就是文档标题的原话，居然没召回**。
查下去：FAQ 入库后**问句只落在 `title`，正文里一个字都没有**，而 BM25 只搜正文。

| 查询字段 | 第 1 名 | 分数 |
|---|---|---|
| 只搜正文 | 机械家平台运费规则 | 9.87 |
| **`title^2` + 正文** | **设备验收有问题怎么办** | **41.50** |

全库 22 篇里 **16 篇**是这种"问句做标题、正文只有答案"的条目。
而这个认识**早在亮点 1 里就用上了**（"喂精排必须带标题"），
**却从来没回头改关键词召回那一环**。

> **边界照实说**：字段缺陷只做了**单条验证**（9.87 → 41.50），
> **全量效果还没重测**——不拿单条结果当整体收益。证据闸阈值也还没按新语料重新校准。

**面试怎么讲**：
1. **主动交代"我的数字被复跑推翻了"，比等面试官问出来强得多。**
   讲清楚错在哪一层、怎么发现的、改成了什么。
2. **口径必须写在数字旁边。** 一个没有口径的指标，经不起一句"你量的是哪一段"。
3. **同一个项目里两处判断标准不一致，是最容易漏的那类 bug**——
   因为每一处单看都有理由，只有放在一起才看得出来。

## 七、面试高频问题

### 7.1 架构与设计

**Q：为什么用多个 Agent 而不是一个 Agent 挂所有工具？**

> 我们项目里两种都用了，按"谁决定走向"分工：
> 业务 Agent 内部是 ReAct（模型决定调什么工具），但**跨域**和**发布**这两条是确定性的。
>
> 单 Agent + 全工具是可行的替代架构——它有个明显好处：**跨域天然不是问题**（它自己决定调几个工具）。
> 但我们没选，代价是明确的：
> - **成本**：每轮都要把全部工具描述塞进上下文让大模型规划。我们现在 **98% 的请求不产生云端费用**，
>   单 Agent 方案会让**每一轮**都走大模型。
> - **权限**：不同角色的工具白名单要做运行时过滤。
> - **可审计**：显式的"意图 → 能力 → Agent"映射比 ReAct 的黑盒决策好审计。
> - 还有一条我们踩过的：**兜底 Agent 刻意不挂工具**——它一旦能查数据，
>   会在路由出错时给出"看似可信其实串了领域"的答案，**掩盖真问题**。
>
> 一句话：**ReAct / plan 是"每轮多花一次大模型"换"不用做路由判定"**，是成本 vs 确定性的取舍。

**Q：LangGraph4j 具体用在哪？**

> 两处，都不是"固定步骤"：
> 1. `AbstractReactAgent` —— 每个业务 Agent 自己是一张 ReAct 图；
> 2. `CompositeGraph` —— 跨域综合，**并行扇出 + 汇总**。
>
> 顺带说一个实现细节：**LangGraph4j 的并行没有公开 API**。翻遍 `StateGraph` 只找到
> `addEdge(String, String)`，没有多源汇合的重载。真相是**隐式**的——
> 给同一个源节点挂多条出边，编译期自动生成合成并行节点；
> **所有分支必须汇合到同一个后继**，否则 `compile()` 直接抛错。
> （`ParallelNode` 是 public 的，但它由编译器生成，不该自己 new。）

**Q：有确定性流程吗？**

> 有，**发布工作流**是纯 Java 状态机，**故意没用 LangGraph4j**：
> 表单字段逐个收集 → **模型只抽字段** → 抽错被校验拦下重填（不会写半截数据）
> → 待确认态 → 一次性确认令牌 → 用户确认 → 校验令牌 → 落库待审核。
>
> 理由是**发布是写操作**，而且这条线是线性、带外部状态（草稿）的——写成状态机比画图清楚。
> 另外 `转人工 / 投诉 / /reset` 也是关键词直接短路、不经模型：这几个**错不起**，
> 而且"转人工"这种词几乎唯一指向——让模型判反而是引入不确定性。

### 7.2 RAG

**Q：检索准不准？**

> **先讲清口径**，我们有两个数：
> 融合层（RRF 取 top-5）**87.5%**；线上真正喂给模型的那 5 条
> （召回 20 → 精排 → 取 5）是 **83.3%**（24 条标注集可复跑）。
> 单路对比：纯向量 87.5%、纯关键词 70.8%。
> **要讲全**：混合与纯向量持平、明显高于纯关键词——所以结论不是"混合最好"，
> 而是"**关键词单路会漏同义改写，必须保留向量路**"。

**Q：这个数字你复跑过吗？**

> 复跑过，而且**正是复跑推翻了我们自己的数字**。原来文档里写的 95.8%，
> 是测于 16 篇 FAQ 小语料、而且只量到融合层。语料长到真实规模后掉到 87.5%，
> 补上线上口径是 83.3%。**教训是：写进文档的数字会过期，而且不会自己报警**——
> 能复跑不等于会复跑。详见亮点 8。

**Q：凭什么说证据闸有效？**

> 标了 34 条样本画阈值曲线 → 发现**向量判据的两类分数区间完全重叠、根本不存在可用分界点**
> （阈值 0.6 时漏放率 100%）→ 换成精排 → **漏放 100% → 0%**。
> **关键是"用数据发现判据选错了"，不是调参调出来的。**
>
> **主动补一句边界**：精排分数分布跟着语料走——语料长到真实规模后零漏放分界从
> 0.191 右移到 **0.582**，而线上阈值还停在 0.19，**所以闸现在是漏的**（漏放 10%）。
> 说明**判据选对之后，阈值仍然要随语料重新校准**。

**Q：检索到的资料不完整怎么办？**

> 踩过一次：文档里明确有「表1 危险一览表」，模型却回答"表1的内容没有提供"。
> 顺着它这句话查下去，发现那张表在**向量路排第 2、却在 RRF 融合后掉出了 top-5**，
> 精排根本没机会看到它。修法是**召回放宽 + 精排收紧**。

**Q：这套 RAG 还有什么不足？**

> 诚实列六条最关键的：
> ① **关键词路搜错了字段**——只搜正文，而库里 16/22 篇的标题才是问句。
> 单条已验证修法（`title^2 + 正文`，9.87 → 41.50 分），**但全量还没重测**；
> ② **证据闸阈值没跟着语料重新校准**——零漏放分界已右移到 0.582，线上还是 0.19；
> ③ **没有 NLI 逐句校验**——角标只保证"编号合法"，不保证"标得对"；
> ④ **没有严格父子块**（`parent_id` 列建了但从未写入），靠"同章节回填"拿到大部分收益，
> 代价是跨章节的长答案看不全；
> ⑤ **没有 Query 改写/扩写**——口语化问法靠 embedding 硬扛；
> ⑥ **评估指标只有 Recall@K**，缺 MRR / Faithfulness / 拒答率，也没做评估集分桶。

### 7.3 工程

**Q：怎么保证 AI 不乱答？**

> 三层：**证据闸**（生成**前**，资料不够就不让开口）→ **提示词硬约束** →
> **生成后自评**（本地小模型核对是否完全基于资料）。另加**数据飞轮**收集答不上来的问题。
> **闸必须在生成前**——生成完再撤回，错话已经说出去了。

**Q：失败了怎么办？**

> 分层降级而不是重试：小模型超时 → 大模型；大模型也不行 → 兜底 Agent；
> 精排挂了 → 退回向量判据（不让外部服务挂了把知识问答整条拖死）。
> **没有自动重试**——超时重试可能重复计费，而且对话场景用户更在意响应速度。

**Q：这套系统最难排查的问题是什么？**

> 是**静默失效**那一类——功能"看起来能用"，只是悄悄做错了事。举三个：
> - **本地小模型冷启动导致分类静默降级**：模型调用统一设了 8 秒超时，
>   而 Ollama 冷启动要十几秒。两层双双超时 → 这句话被判成 UNKNOWN → 静默降级到兜底。
>   **用户只觉得"答得敷衍"，从现象上根本看不出是超时。**
>   这条逼出了"审计里必须先记下分类依据"这个改动。
> - **会话粘性把完整的新问题当追问吃掉**：判据写成"关键词没命中就用粘性"，
>   而"关键词没命中"不等于"是追问"——用户连问两个知识类问题，全被粘在设备 Agent 上。
> - **兜底分支返回不可变 `List.of()`**：`set()` 抛 `UnsupportedOperationException`
>   → 整篇 OCR 文字全丢，只留一条读起来像"少了个小功能"的 warning。
>
> 共同点是**都不报错**。所以后来的习惯是：**先做可观测性，再谈修问题。**

## 十、面试前 5 分钟速览

**如果只让你讲三件**：
1. **证据闸判据选错**（亮点 1）——体现你会用数据判断"方向对不对"，而不是调参调到满意
2. **用词表的第三次翻车 → 把"定案"降级成"提示"**（亮点 4）——体现你知道**同一条判据在不同位置风险不同**
3. **用户一句"这不就是求租吗"揪出重复意图**（亮点 5）——体现你会**从业务直觉反推结构问题**

**如果还能多讲一件**（这也是最近发生的）：
4. **指标被复跑推翻**（亮点 8）——数字过期、口径量错段、同一个认识没用到所有地方。
   **主动说"我原来的数字是错的、错在哪、怎么发现的"，比只讲成功更可信。**

**必须带上的数字**：96.8%（61/63）、98% 不产生云端费用、**Recall@5 线上口径 83.3%**、161 个测试。

**一定要主动说的边界**：
- 关键词路漏搜标题字段——**已定位、单条已验证修法，但全量还没重测**（不拿单条当整体收益）
- 证据闸阈值没跟着语料重校准，**当前漏放 10%**（不是原来记录的 0%）
- 角标只保证编号合法、不保证标得对（NLI 没做）
- 跨域现在完全靠模型判，没有独立召回
- 混合检索**没跑赢纯向量**（结论是"关键词单路会漏同义改写"，不是"混合最好"）
