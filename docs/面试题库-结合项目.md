## 〇、先建立"坐标系"——这份题库和你项目的错位在哪

**先说清楚一件事**：网上流传的 AI Agent 面经（字节那份是典型），**题目几乎全是照着
"Coding Agent / 通用任务型 Agent"出的**——多 Agent 改同一个文件、Plan 模式、MCP、
上下文压缩、长期记忆。而你做的是**业务客服 Agent**。

**这个错位不是劣势，但你必须主动处理它**，否则会出现两种翻车：

| 翻车方式 | 长什么样 |
|---|---|
| **硬蹭** | 面试官问"多个 Agent 怎么改同一个文件"，你说"我们 Agent 也写文件"——**一问就穿** |
| **摆烂** | 你说"我们是客服，没这些"——面试官会认为你**没做过通用 Agent 工程** |

**正确的姿势是三段式**：

1. **先答通用原理**（证明你懂这题在问什么）；
2. **再讲本项目里最接近的那件事**（证明你做过同构的问题）；
3. **最后照实说边界 + 补齐方案**（证明你知道差在哪、也想清楚了怎么补）。

> **一句话把项目讲清楚**（开场就要用，后面所有题都挂在这上面）：
>
> 我做的是一个**二手工程机械平台的 AI 客服/导购 Agent**（Spring Boot 4.1 + Spring AI 2.0 +
> LangGraph4j）。它不是"套壳聊天"，有四条硬约束贯穿始终：
> **规则类问题资料不足就不许开口**（防编造平台规则）、**写操作必须确定性**（发布要落库）、
> **98% 的请求不产生云端费用**（高频客服场景）、**路由结论可解释可审计**。
>
> 这四条约束决定了它和通用任务型 Agent 的**设计取向完全不同**：
> **通用 Agent 是"给模型更多自主权"**（它自己规划、自己调工具、自己判断做完没有）；
> **我做的是"把自主权精确地切给模型该有的那部分"**——该让它决定的（这句话什么意思、
> 该查什么）全给它，**不该让它决定的（流程走向、能不能开口、写不写库）一点都不给**。

**一句话记住这个取向**：**按"谁来决定走向"分工。**

## 一、项目与架构

### Q1. 简单介绍一下你的 Agent 项目，以及整体架构设计

**标准答法**：讲清三件事——**做什么的、有几个角色、它们怎么协作**。
不要一上来讲技术栈，先讲业务问题。

**落到本项目**：

> **业务**：机械家是二手工程机械交易平台。用户可以用自然语言**找设备、找出租、找活、
> 问平台规则**，也能让助手**代他发布**出租/求租，答不上来转人工。
>
> **架构分四层**（从下往上）：
>
> | 层 | 做什么 | 关键设计 |
> |---|---|---|
> | **接入/鉴权** | 聊天、SSE 流式、登录令牌 | 必须登录——能查平台侧数据、能代发布，匿名没法做权限控制 |
> | **路由层** | 7 步路由链 + 会话粘性 + 指代消解 | 显式的"意图 → 能力 → Agent"映射，结论落 `ai_audit_log` 可审计 |
> | **执行层** | 5 个业务 Agent + 7 个 `@Tool` | 三种编排范式（见下） |
> | **知识层** | 混合召回 + 精排 + 证据闸 + 自评 + 飞轮 | 独立于 Agent 的一条路（为什么独立，见 Q20） |
>
> **三种编排范式，按"谁决定走向"分工**：
>
> | 编排方式 | 用在哪 | 谁决定走向 |
> |---|---|---|
> | **ReAct 图**（LangGraph4j `ReactAgent`） | 每个业务 Agent 内部 | **模型**决定调什么工具、几步 |
> | **并行扇出图**（`CompositeGraph`） | 跨域问题综合 | **代码**决定扇出，各域内部仍是 ReAct |
> | **确定性状态机**（纯 Java） | 发布工作流 | **完全由代码决定**，模型只抽字段 |
>
> **5 个 Agent**：设备查询 / 出租求租 / 知识问答 / 发布 / 兜底。
> **兜底 Agent 刻意不挂任何工具**——它一旦能查数据，就会在路由出错时给出
> "看似可信其实串了领域"的答案，**掩盖真问题**。宁可让它老实说"我帮不上忙"。

**面试官想听什么**：你有没有**架构判断力**，而不是会不会堆框架。
"三种编排范式"这个分类本身就是答案。

### Q2. ReAct 模式和 Plan 模式有什么区别？分别适用哪些场景？

**标准答法**：

| | ReAct | Plan-and-Execute |
|---|---|---|
| 怎么走 | 边想边做：Thought → Action → Observation 循环 | 先出完整计划，再逐步执行 |
| 优点 | 灵活、能根据中间结果调整、不需要预先知道步骤 | 全局视野、步骤可审、长任务不跑偏 |
| 缺点 | 短视、可能绕路、步数不可控 | 计划一旦错了全错；环境变了不会改 |
| 适用 | **步骤数不确定、依赖中间结果**的任务（查数据、问答） | **步骤可枚举、需要人审**的长任务（写代码、跑流程） |

**落到本项目——我们两种都用了，这正是本项目的核心设计判断**：

> 我们没有用"Plan-and-Execute"这种**让模型生成计划**的形态，但项目里有**两种"预定义计划"**：
>
> 1. **发布工作流**——纯 Java 状态机，**故意没用 LangGraph4j**。
>    表单字段逐个收集 → 模型只抽字段 → 校验 → 待确认 → 一次性令牌 → 落库。
>    **为什么不用图**：发布是**写操作**且**线性**，还带外部状态（草稿、令牌）。
>    写成状态机比画图清楚，而且"模型不能决定流程"这条约束在代码层面就是硬性的。
> 2. **跨域综合**——扇出哪些 Agent 由**代码**根据命中的领域决定，各域内部才是 ReAct。
>
> **一句话**：**ReAct 是"把走向交给模型"换灵活，Plan/状态机是"把走向收回来"换确定。**
> 选哪个不看哪个先进，看**这件事错得起错不起**——发布错不起，所以收回来；
> "这句话该查设备还是查知识"错得起（大不了重问），所以交给模型。

**⚠️ 边界**：我们没有做**模型自主生成计划**（真正的 Plan-and-Execute），
因为业务里没有那种"步骤要模型临场规划"的任务。如果要做（比如"帮我比价 3 台设备再生成对比报告"），
我会用 Plan 模式：先让模型出步骤 → 人确认或代码校验 → 再逐步执行。

### Q15. Multi-Agent 系统中，不同 Agent 之间应该如何划分职责？

**标准答法**：三种常见划分维度——**按业务域**（各管一摊）、**按角色**
（planner / executor / critic / router）、**按工具**（谁有权限用谁）。**最常见也最稳的是按业务域。**

**落到本项目**：

> 我们**按业务域划分**，不是按角色。理由是客服场景里**领域之间有天然的数据边界**：
> 设备表、出租表、知识库是三套不同的数据和工具，按域切最自然，权限也最好控。
>
> | Agent | 职责 | 挂了什么工具 |
> |---|---|---|
> | EquipmentAgent | 设备买卖查询 | `equipment` |
> | RentalAgent | 出租 + 求租查询 | `chuzu` / `qiuzu` |
> | KnowledgeAgent | 平台规则 + 行业资讯 | `policy` / `news` |
> | PublishAgent | 发布出租/求租 | `publish` |
> | GeneralAgent（兜底） | 闲聊、认不出的话 | **不挂任何工具** |
>
> **三条硬规则**：
> 1. **意图到 Agent 是显式映射表，不是让模型猜**——"意图 → 能力 → Agent"，
>    配优先级 + 角色权限。好处是**可审计**：能回答"这句话为什么交给了这个 Agent"。
> 2. **工具按角色运行时过滤**——同一个 Agent，不同角色拿到的工具不同。
>    ⚠️ 这里踩过坑：**编译好的 ReAct 图是按工具集合缓存的**，
>    缓存键里**必须带上工具集合**，否则不同角色会复用同一张图，**等于绕过了白名单**。
> 3. **兜底 Agent 不挂工具**（见 Q1）。
>
> **一个真实的教训**：我们的"求租"和"用机需求"原本是两个意图、两个工具，
> 而**业务上它们是同一件事**（平台只是建了两张表）。两个几乎同义的选项摆在模型面前，
> 判歪是必然的——**删掉那个重复意图后，意图准确率涨了 1.6 个百分点**
> （95.2% → 96.8%）。
> **结论：多 Agent 划分的第一原则不是"能分开"，而是"该分开"。
> 分类体系里有个重复项，比分类不准更致命。**

## 二、上下文与记忆（必问区）

> **先给结论**：这一块是本项目和"通用 Coding Agent"**差距最大**的地方。
> 通用 Agent 面对的是"几十万 token 的代码库"，必须做压缩；
> 我们面对的是"客服对话，单轮很短"，历史只有 **5 轮定长滑窗**，**没有压缩机制**。
> **照实说，然后讲清楚我们的替代方案是什么。**

### Q3. 如果 Agent 上下文信息越来越长、超过模型限制，通常有哪些处理方式？

**标准答法**：按"丢什么"分五类，从粗到细：

| 方式 | 做法 | 代价 |
|---|---|---|
| **截断/滑窗** | 只留最近 N 轮 | 最简单，但会丢掉早期约束 |
| **摘要压缩** | 把旧对话交给模型总结成一段 | 有信息损失，且摘要本身要花一次调用 |
| **分层记忆** | 近期原文 + 远期摘要 + 关键事实常驻 | 结构复杂 |
| **检索式记忆** | 历史向量化，按当前问题召回相关片段 | 需要额外存储和检索链路 |
| **状态外置** ⭐ | **把状态从 context 里搬到外部存储**，模型需要时再查 | 要设计状态机，但**最彻底** |

**落到本项目**：

> 我们做的是**第一类（定长滑窗）+ 第五类（状态外置）**，**没做摘要压缩**。
>
> **① 滑窗**：`ChatService.HISTORY_ROUNDS = 5`，喂给模型的对话历史是**最近 5 轮**
> （`ConversationMemory.recentMessagesForModel` 从 MySQL 取 `rounds * 2` 条）。
> 指代消解也是用最近 5 轮（"那台"→ 完整问题）。
> ⚠️ **边界**：这个 5 是**硬编码常量**，不是配置项——业务上够用，但严格说是没做自适应。
>
> **② 状态外置——这才是我们真正防"上下文超限"的手段**：
> 我们把**所有需要跨轮记住的东西都搬出了对话**：
>
> | 状态 | 放哪 | 为什么不放 context |
> |---|---|---|
> | 会话粘性（上轮意图、上轮 Agent） | **Redis** `StickySessionStore` | 每轮都要用，放 context 里既费 token 又可能被截断 |
> | 发布草稿（已收集的字段） | **MySQL** 草稿表 | 这是**要落库的写操作**，必须持久、必须能校验 |
> | 一次性确认令牌 | 服务端（带有效期 + 是否用过） | 安全相关，**绝不能交给模型复述** |
> | 对话原文 | **MySQL** `ai_conversation` / `ai_message` | 按需取，而不是全塞 |
>
> **核心思路**：**不要让模型"记住"任何一件事——让它"查得到"。**
> 模型记不住的（也可能被压缩掉），存起来就永远不会丢。
>
> **③ 知识侧的"超限"是另一种形态**：RAG 检索回来的资料也可能撑爆窗口。
> 我们的做法是**父子块 / 表格摘要模式**：**检索入口是短的（摘要），本体存库不向量化**，
> 命中后再按 `tableId` / `section_path` 取回。**"短的负责被找到，长的负责被读懂。"**

**面试官想听什么**：大多数人只会答"滑窗和摘要"。**"状态外置"这一层是区分度所在**——
它说明你意识到 **context 不是唯一的记忆载体**。

**⚠️ 照实说的边界**：我们没有摘要压缩，也没有 `ConversationContextPolicy`——
**LangGraph4j 其实提供了这个 API**（`ReactAgentBuilder.conversationContextPolicy(...)`），
我们没接。如果对话轮数真的会很长（比如用户连续问 30 轮），现在的滑窗会丢掉早期约束。

### Q4. 上下文压缩时一般会保留哪些关键信息？如何判断哪些内容可以被丢弃？

**标准答法**：

**必须保留**（丢了会出事）：① 用户的目标与硬约束（"预算 20 万以内""只要洛阳的"）；
② 已达成的结论与决策（"已经确认了设备 A"）；③ 未完成的待办与当前进度；
④ 工具调用的**关键结果**（不是原始返回，是结论）；⑤ 错误与失败原因（避免重蹈覆辙）。

**可以丢弃**：① 寒暄与确认性废话；② 被后续结论覆盖的中间推理；
③ 重复的尝试过程（只留"试过 X，失败，原因 Y"）；④ 大块原文（**改成存引用/ID**）。

**判断标准一句话**：**"如果这句话没了，下一步会不会做错？"** 不会就可以丢。

**落到本项目**：

> 我们**没做压缩**，但**这个判断标准我们是用另一种方式实现的**——
> **凡是不允许被丢掉的东西，我们压根不放进 context**（见 Q3 的状态外置表）。
>
> 最典型的例子是**发布工作流**：用户在 5 轮里陆续说"出租一台小松 200，
> 洛阳，月租 8000，可以带司机"——这些字段**每一个都落在 MySQL 的草稿里**，
> 不依赖模型记住。到确认那一步，我们**用草稿渲染确认摘要**给用户看，
> 而不是让模型复述。**这样即使对话被截断，字段也不会丢。**
>
> **另一个真实场景**：`PublishAgent` 抽字段时**只取用户说的话，不取助手的回复**——
> 因为助手的确认摘要里含令牌和梳理过的文案，**回灌进去会污染抽取**。
> 这也是一种"该丢什么"的主动判断。

### Q5. 如何避免 Context 压缩之后，模型忘记用户之前提出的重要需求？

**标准答法**（四条，按可靠性排序）：

1. **别让它依赖记忆**——把硬约束**抽成结构化字段常驻**（写进状态或系统提示词），
   每轮显式重放。**这是最可靠的一条。**
2. **压缩时把约束"钉"住**——摘要模板里强制包含"用户约束"字段，不参与丢弃。
3. **每轮做一次约束回放**——在 prompt 里固定位置重述当前约束。
4. **加了新约束就冲突检测**——用户说"预算改成 30 万"时，要显式覆盖旧值。

**落到本项目**：

> 我们走的是**第 1 条**，而且做得很彻底：
> **发布这条线的所有字段都是结构化状态，模型只负责"从这句话里抽"，不负责"记住"。**
>
> 具体是：`PublishAgent` 每轮把用户话里的字段抽出来 → `PublishValueValidator` 校验
> → 写进草稿 → **下一轮追问缺失项时，是从草稿里读"还差哪些字段"，不是问模型**。
> 字段抽错了会被校验拦下重填（**绝不会写半截数据**）。
>
> **这条路的好处不止是"不会忘"**：它还让**流程完全可测**——
> 我们可以直接断言"给出这串输入，草稿里应该有这几个字段"，
> 不需要跑模型。178 个测试里这类占了不少。
>
> **顺带一个反例**（说明"让模型记"有多不靠谱）：我们的**会话粘性**最早写成
> "关键词没命中就用上轮的 Agent"，结果用户连问两个知识类问题，全被粘在设备 Agent 上——
> **因为"关键词没命中"不等于"这是追问"**。后来改成只认指代词。
> 这个坑的教训是：**用形态判据去猜语义，必然出错**（踩坑第 41、48 条）。

**⚠️ 边界**：我们**没有**跨会话的长期记忆，所以"用户上周说过预算 20 万"这种是记不住的。
客服场景下我们判断这个价值不高（用户每次问的大多是独立问题），
**而且有合规风险**（把用户偏好长期存下来需要额外授权）。如果要做，见 Q7。

### Q6. Agent 执行任务时出现路径反复、重复尝试等"路径震荡"问题，可能原因是什么？如何优化？

**标准答法**：

**原因**（按常见度）：
1. **工具描述重叠**——两个工具看起来都能干这事，模型来回试；
2. **缺少终止判据**——模型不知道自己已经做完了；
3. **错误信息不具体**——工具返回 `"失败"` 而不是 `"参数 area 必须是地级市名，你传的是'洛阳'——请改成'洛阳市'"`，
   模型只能盲试；
4. **状态不清晰**——上下文里没有明确的"已做过什么、结果如何"，模型重复劳动；
5. **没有步数/成本上限**——震荡没人兜底。

**优化**：
- 工具描述**写清边界与反例**（"查出租用 A，查求租用 B，**A 不接受'我要找活'这种需求描述**"）；
- 错误信息**给出下一步动作**，而不是只报失败；
- 显式维护**执行轨迹**（做过什么、结果如何）放进状态；
- 设 **max steps / 预算上限**，超了强制收敛到兜底；
- **重复调用检测**：同样的 (工具, 参数) 连续调用 N 次就直接判死。

**落到本项目**：

> **我们有一半的防线，另一半确实没做，照实说。**
>
> **做了的**：
> - **工具描述带边界**：`search_chuzu` 的参数描述里直接写了可选值
>   （"吨位档位，可选值：6吨以下、6-9吨…"），不给模型盲试的空间；
> - **分层超时**：小模型 8 秒 / 大模型 / 精排挂了退回向量判据——**不让外部服务把整条链拖死**；
> - **兜底话术**：Agent 执行抛异常时**必须降级成一句人话**，不能把异常抛给用户
>   （`AbstractReactAgent.reply` 的 catch 里返回 `fallbackReply()`）；
> - **审计**：每轮落 `ai_audit_log`（意图、置信度、命中层、路由阶段）——
>   出事能复盘。
>
> **⚠️ 没做的（这是真实风险）**：
> 1. **没有显式设步数上限**——我们调 `graph.invoke(map)` 时**没传 `RunnableConfig`**
>    （LangGraph4j 的 `RunnableConfig` 是有 `recursionLimit` 的），用的是库的默认保护。
>    也就是说**我们依赖框架的兜底，而不是自己的预算控制**。
> 2. **没有重复调用检测**（同样的工具+参数连调 N 次）。
> 3. 我们的工具是**查询类为主**，天然幂等、"试错"成本低，
>    所以这个风险在业务上没暴露出来——**但这不等于没问题**。
>
> **如果要做**：我会先加 `RunnableConfig.recursionLimit` 把步数卡死，
> 再加一层"同一 (工具, 参数) 连续调用 2 次就中断"的检测，最后把震荡事件也记进审计表。
> **顺序是先能看见（审计）、再能防住（上限）、最后才谈优化。**

### Q7. 一个完整的 Agent 记忆系统应该如何设计？包括哪些模块？

**标准答法**：分层是三层的经典结构

| 层 | 存什么 | 生命周期 | 载体 |
|---|---|---|---|
| **工作记忆**（Working） | 当前任务的中间状态、工具结果 | 单次任务 | Context / 状态对象 |
| **会话记忆**（Episodic） | 本次对话的历史、用户本次的目标 | 单会话 | DB / Redis |
| **长期记忆**（Semantic / Profile） | 用户画像、稳定偏好、跨会话事实 | 长期 | 向量库 + 结构化表 |

**配套四个模块**：**写入**（什么时候记）、**提取**（从对话里抽什么）、
**存储**（结构化 vs 向量）、**检索**（什么时候取回来、怎么排序）。

**落到本项目——照实说，我们只有中间一层**：

> | 层 | 我们有没有 | 具体是什么 |
> |---|---|---|
> | 工作记忆 | ✅ | `AgentContext`（history + tools + 当前问题），单次请求内有效 |
> | 会话记忆 | ✅ | MySQL `ai_conversation` / `ai_message`（对话原文）+ Redis `StickySessionStore`（上轮意图/Agent）+ MySQL 发布草稿 |
> | **长期记忆** | ❌ | **没有用户画像、没有跨会话记忆、没有向量化记忆检索** |
>
> **为什么没做长期记忆——三条理由，都是想过的**：
> 1. **业务价值低**：客服场景用户问的大多是独立问题（"押金怎么退"），
>    跨会话记住"他上次问过押金"没什么用；
> 2. **合规成本高**：把用户偏好长期存下来，需要额外授权和清理机制；
> 3. **我们有更便宜的替代**：真正需要"记住用户"的地方是**发布工作流**，
>    而我们用的是**结构化草稿**，比向量记忆更准、可校验、可审计。
>
> **如果要做，我会这么设计**：写入端只抽**高置信、稳定、可复用**的事实
> （"常用地区：洛阳""偏好二手而非新机"），**不抽敏感信息**；
> 存储上用"结构化字段 + 自然语言事实"两条腿（前者可精确过滤，后者可模糊召回）；
> 检索上**不要每次都召回**——只在路由到相关意图时才注入，控制 token 和噪声。

### Q8. 当前对话中的 Context 和长期 Memory 有什么区别？两者分别解决什么问题？

**标准答法**：

| | Context（当前对话） | Memory（长期） |
|---|---|---|
| 时间范围 | 本次会话 | 跨会话 |
| 存什么 | 原文 + 本轮状态 | 抽取后的**结论/事实** |
| 谁在用 | 模型直接读 | 检索后注入 context |
| 解决 | **"刚才说到哪了"** | **"这个用户是谁、习惯是什么"** |
| 成本 | 每轮都在烧 token | 存着几乎不花钱，**取的时候才花** |
| 风险 | 超限、丢信息 | 存错、过期、隐私 |

**一句话**：**Context 是"工作台"，Memory 是"档案柜"。**
工作台要小要顺手，档案柜要大要能查。

**落到本项目**：

> 我们的区分很清晰：
> - **Context = 最近 5 轮对话 + 当前问题**（`ConversationMemory.recentMessagesForModel`）；
> - **Memory = 会话粘性（Redis）+ 发布草稿（MySQL）**——**但严格说这是"会话状态"，
>   不是"长期记忆"**，因为它随会话结束就没了。
>
> **这个区分带来一个很实际的设计后果**：
> 我们把东西放哪个层，**取决于"它下次还要不要用"**——
> - "上轮路由到了 RentalAgent" → 下次还要用 → **Redis**（跨请求）；
> - "用户说了月租 8000" → 落库前一直要校验 → **MySQL 草稿**（跨请求、要持久）；
> - "用户刚才说'你好'" → 只影响这轮语气 → **context**（请求内）。
>
> 而**知识库（RAG）其实是一种特殊的"长期记忆"**——存的是平台规则这类稳定事实，
> 靠向量检索取回来。区别是它是**平台共享的**，不是**用户个人的**。

### Q9. Agent 中的 Memory 信息如何进行提取、存储和检索？

**标准答法**：
- **提取**：对话结束后（或每轮）用小模型做一次结构化抽取，产出
  `{类型, 内容, 置信度, 时效}`；**只抽稳定的、可复用的、非敏感的**。
- **存储**：两类——**结构化字段**（可精确过滤，如"城市=洛阳"）+
  **自然语言事实向量化**（可模糊召回，如"用户倾向于买二手"）。
- **检索**：**不要无脑注入**。按当前意图决定要不要召回；召回后按
  **相关度 × 时效 × 置信度**排序，控制条数与 token 预算。

**落到本项目**：

> 我们没有做用户长期记忆的提取与检索，但**同样这套"提取 → 存储 → 检索"的模式，
> 我们在三个地方用得很扎实**——面试时可以直接拿这三个当答案：
>
> | 场景 | 提取 | 存储 | 检索 |
> |---|---|---|---|
> | **发布字段** | 模型从用户话里抽（**只取用户说的，不取助手回复**） | MySQL 草稿（结构化） | **不用检索**——每轮从草稿读缺失项 |
> | **知识库** | 文档解析 + 切片（LiteParse / 多模态 OCR） | ES（切片向量）+ MySQL（**表格本体不向量化**） | 混合召回 → 精排 → 证据闸 |
> | **数据飞轮** | 答不上来的问题自动收集 | MySQL（待审队列） | 人工补答案后回灌知识库 |
>
> **这三条的共同点**：**都是"把非结构化的话变成结构化的事实，然后让代码去用它"**，
> 而不是"让模型再读一遍"。
>
> **一个值得讲的细节**（提取环节的真实教训）：
> `PublishAgent` 抽字段时**故意只喂用户说的话**——因为助手回复里的确认摘要
> 含有令牌和梳理过的文案，**回灌会污染抽取**（模型可能把"我复述的"当成"用户说的"）。
> **提取之前先想清楚"这份输入干不干净"，比调提示词更重要。**

### Q10. 为什么一些记忆管理、上下文压缩任务可以交给小模型完成？相比大模型有什么优势？

**标准答法**：因为这类任务**"窄但不难"**——比的是**稳定性**，不是**推理深度**。

| 优势 | 说明 |
|---|---|
| **成本** | 差一到两个数量级；高频任务必须省 |
| **延迟** | 小模型响应快，交互场景体感差距明显 |
| **可控/可本地** | 能离线、数据不出域（合规） |
| **任务匹配** | 抽取/分类/摘要的答案是**有明确形态的**，大模型的多余推理反而增加不确定性 |

**关键前提**：**必须有兜底**——小模型判不了要能升级给大模型，不能硬扛。

**落到本项目——这就是我们的核心架构**：

> 我们的**三层意图识别**就是这件事：
>
> | 层 | 占比 | 成本 |
> |---|---|---|
> | 关键词加权 | **40%** | 零成本、毫秒级、**可复现** |
> | 本地小模型（Ollama qwen2.5:7b） | **59%** | **免费**（本地） |
> | 云端大模型（MIMO） | **2%** | 唯一有费用的部分 |
>
> **98% 的请求不产生云端费用。**
>
> **生成后的自评**（"答案是否完全基于资料"）也是**本地小模型**做的——
> 同样的理由：这是"核对"，不是"创造"。
>
> **⚠️ 用小模型必须解决的两个真问题**（这是我们踩出来的）：
>
> 1. **冷启动**：本地模型冷启动要**十几秒**，而我们的模型调用统一设了 **8 秒**超时——
>    两层双双超时 → 这句话被判成 `UNKNOWN` → **静默降级到兜底**。
>    用户只觉得"答得敷衍"，**从现象上根本看不出是超时**。
>    修法是**小模型预热**（`SmallModelWarmup`，实测 939ms）+ 超时按层设置。
>    这个坑逼出了"审计里必须先记下分类依据"这个改动。
> 2. **小模型会缺证据**：发布意图那条路上，7B 模型**缺"主体是机主"的证据**，
>    光靠它判不出来。所以最后定的是**"关键词层认出发布意愿 → 当提示交给模型"**，
>    不是全靠小模型。
>
> **面试官想听什么**：别只说"小模型便宜"。**说清楚"什么样的任务适合小模型"
> （窄、有明确形态、可兜底）以及"用小模型会引入什么新问题"（冷启动、能力上限）。**

## 三、工具与协议

### Q11. MCP 是什么？Agent 通过 MCP 调用工具的流程是什么？

**标准答法**：
**MCP（Model Context Protocol）是一套把"工具/数据源"标准化暴露给模型的协议**——
本质是**把"函数调用"从一个进程内的约定，变成一个跨进程、跨厂商的接口标准**。

**调用流程**：客户端（Agent 宿主）连 MCP Server → 通过 `tools/list` 拿到工具清单与
JSON Schema → 把清单转成模型能看的工具定义 → 模型输出工具调用意图 →
客户端通过 MCP 发给 Server 执行 → 结果回灌模型。

**它解决的核心问题**：**工具的"写一次，处处可用"**——
不用为每个 Agent 框架重写一遍工具适配层；工具可以独立部署、独立扩缩容、独立授权。

**落到本项目——我们没用 MCP，照实说，并说清为什么**：

> 我们用的是 **Spring AI 的 `@Tool` 注解**（进程内方法调用），**不是 MCP**。
>
> **为什么不需要**：
> - 工具是**我们自己写的**、跑在**同一个进程**里，编译期就知道有哪些；
> - 没有"跨进程/跨厂商复用"的需求；
> - 进程内调用少一层网络和序列化，**延迟更低、排障更简单**。
>
> **我们的工具层长这样**：每个工具实现 `BizTool` 标记接口 + 方法上标 `@Tool`。
> 用标记接口而不是扫包找 `@Tool`，是因为
> **能力标识（capability）是编译期就能确定的信息**，显式声明比运行时反射更可审计。
>
> **⚠️ 什么时候该上 MCP**：如果要把平台能力开放给**第三方客户端**，
> 或者工具要**独立部署/独立授权**（比如"查设备"这个能力被好几个团队用），
> **那 MCP 才是对的形态**。这是个明确的演进方向，不是"我们不知道 MCP"。

### Q12. 当 Agent 拥有大量工具时，如何避免工具描述导致 Prompt 过长？

**标准答法**（按有效性排序）：

1. **别让模型看见不该用的工具** ⭐ —— 按 Agent / 角色**过滤工具集**，
   这是最有效的一招（不是压缩描述，是**根本不给**）；
2. **工具描述写紧** —— 名字自解释、描述只写**边界与反例**，不写废话；
3. **分层/分组** —— 先让模型选"类别"，再给该类别的工具（两段式）；
4. **检索式工具选择** —— 工具太多（几百个）时，把工具描述向量化，
   按当前问题召回 top-K 个工具再注入。

**落到本项目**：

> 我们只有 **7 个工具**，所以问题不尖锐，**但我们的做法恰好是第 1 条**：
>
> - 工具**按 Agent 挂**，不是全局共享——每个 Agent 只挂自己那几个
>   （KnowledgeAgent 挂 2 个，EquipmentAgent 挂 3 个，**兜底 Agent 挂 0 个**）；
> - 再叠加**角色白名单运行时过滤**——同一个 Agent，不同角色看到的工具也不同；
> - 所以模型实际看到的工具定义数是 **0~3 个**，而不是 7 个。
>
> ⚠️ **这里有一个真踩过的坑，值得讲**：ReAct 图是**编译后按工具集合缓存**的
> （同一个工具集合只编译一次，省构图开销）。**缓存键里必须带工具集合**——
> 否则不同角色会复用同一张图，**白名单形同虚设**。这是"性能优化顺手把安全做没了"的典型。
>
> **另外**：我们的工具描述**不写"你能干什么"的废话，只写参数和边界**。
> 比如 `search_chuzu` 的参数里直接枚举了吨位档位的可选值，
> 模型不用猜、也不会瞎传。

**⚠️ 边界**：如果工具真涨到几十个，现在的"按 Agent 挂"就不够了，
需要上第 4 条（检索式工具选择）。**我们没做，因为 7 个工具还不需要。**

### Q13. 如果工具返回的数据量过大，超过上下文窗口限制，应该如何处理？

**标准答法**：
1. **源头控量** —— 工具本身带分页 / `limit`，**默认值就要小**；
2. **两段式** —— 先返回摘要 + ID，模型确需要再调"取详情"（**我们项目里的父子块就是这个思路**）；
3. **服务端裁剪** —— 返回前只保留模型真正要用的字段（不要整个 DTO 序列化进去）；
4. **结果归约** —— 大结果先过一个小模型做抽取/摘要，只把结论回灌；
5. **外置 + 引用** —— 大块内容存起来，context 里只放引用（ID / 路径）。

**落到本项目**：

> 我们的两种工具正好对应两端：
>
> **① 查询类工具（`search_*`）——用第 1 条：源头控量。**
> 每个查询工具都有 `limit` 参数，**描述里直接写死"默认 5，最大 20"**，
> 模型没法一次捞 1000 条。
>
> **② 知识类（RAG）——用第 2 条：两段式。**
> 这是我们做得最讲究的地方：
> **检索入口是"表格摘要"（文档标题 + 表格标题 + 表头 + 前 5 行 + 共 N 行），
> 本体（完整表格 markdown）不切片、不向量化，结构化存在 MySQL 里。**
> 命中摘要后按 `tableId` **取回完整表格**。
> 正文同理：切片带 `section_path`，命中后**回填同章节的邻块**。
>
> **一句话**：**短的负责被找到，长的负责被读懂。**
> 这样"检索精度"和"生成质量"这两个互相矛盾的要求被拆到了两个对象上。
>
> **⚠️ 边界**：我们**没有做"回填之后再截断"**。如果命中的表格有几百行，
> 它会被**完整**喂给模型——目前靠证据闸 + 生成提示词约束撑着，
> **没有按 token 预算做二次裁剪**。这是已知缺口。
> 真要做的话，我会在回填那一步加一个 token 预算：超了就只喂表头 + 命中行附近的若干行，
> 并明确告诉模型"这是节选"。

## 四、性能与成本

### Q14. Prompt Cache 是什么？它为什么能够提升模型调用效率？如何提高缓存命中率？

**标准答法**：
**Prompt Cache 是复用"相同前缀"的 KV 缓存**。Transformer 推理时，
每个 token 的 Key/Value 都要算一遍；**前缀相同**的话，这部分 KV **可以复用**，
省掉重复计算 → **降低延迟、降低成本**（多数厂商对命中部分按更低价格计费）。

**提高命中率的原则**：**把"稳定的内容"放前面，"变化的内容"放后面**——
因为缓存是**前缀匹配**，一旦中间有一处不同，后面全部失效。

具体做法：
1. **顺序固定**：system prompt → 工具定义 → 长期背景 → 会话历史 → 当前问题；
2. **别在稳定前缀里插变化量**（时间戳、随机 ID、用户昵称）；
3. **少改 system prompt / 工具定义**（改一次，全量缓存失效）；
4. **多轮对话天然受益**：前缀就是历史，所以历史**追加式**增长时命中率最高。

**落到本项目——照实说，我们没有做显式的 Prompt Cache 优化**：

> **⚠️ 边界**：我们没有主动配置或度量过 prompt cache，
> **也没有把"缓存命中率"当成一个指标去优化**。所以这题我只能答通用原理 + 讲我们天然占优的地方。
>
> **我们天然符合几条原则**（算是无意中做对了）：
> - **系统提示词从 `.md` 文件加载**（9 个提示词文件），**内容稳定、顺序固定**，
>   不是每轮动态拼的——这保证了前缀稳定；
> - **工具定义按 Agent 固定**（而且图是按工具集合缓存的），同一个 Agent 的工具描述不变；
> - **多轮对话是追加式**的（历史按时间正序拼在前面）；
> - **每个 Agent 一个独立提示词文件**，不会互相污染。
>
> **但我们也有一处明显会打掉缓存的写法**：
> 我们把**会话历史直接拼在 system 之后、当前问题之前**——
> 如果历史被截断（超出 5 轮滑窗），**前缀会整体位移，缓存全失效**。
> 更稳的写法是把"固定的 system + 工具定义"压在最前面且**绝不改动**。
>
> **如果要做优化**，我会按这个顺序：
> ① 先**度量**（在请求里读厂商返回的 cached token 数，建个指标）；
> ② 再**固定前缀顺序**，把可能变的东西（时间、用户信息）挪到最前面之后；
> ③ 最后才谈"要不要把长 system 拆成稳定段 + 可变段"。
> **没有度量就说"我优化了缓存"，那是猜。**

**面试官想听什么**：这题很多人会背原理但说不出"我的项目里哪里会打掉缓存"。
**能指出自己项目里破坏缓存的那一行，比背对原理更加分。**

### Q18. 为什么一些场景（如车载 Agent）会采用小模型初步召回，而不是直接调用大模型？

**标准答法**：车机场景的特殊约束放大了小模型的优势——

| 约束 | 为什么小模型合适 |
|---|---|
| **断网/弱网** | 云端不可用，**本地模型是唯一选择** |
| **延迟敏感** | 驾驶场景要求毫秒~百毫秒级，云端往返做不到 |
| **高频** | 每句话都上云，成本和流量都不可接受 |
| **任务窄** | 唤醒、意图初筛、指令抽取——**答案空间小**，小模型够用 |
| **隐私** | 车内语音/位置数据不出车 |

**通用原则**：**"初筛"这个环节的性质决定的**——它是**高召回、低精度要求**的一步，
目的只是**把大模型要处理的量降下来**，判错了还有兜底。

**落到本项目——这是同一个问题的非车载版本**：

> 我们的**三层意图识别**就是这个结构：
>
> | 层 | 占比 | 说明 |
> |---|---|---|
> | 关键词加权 | 40% | **零成本、毫秒级、完全可复现**——比小模型还便宜 |
> | 本地小模型（qwen2.5:7b） | 59% | 免费、本地、无网络依赖 |
> | 云端大模型 | **2%** | 只有前两层都不行才用 |
>
> **换算一下**：**98% 的请求不产生云端调用**。
> 平台客服是高频场景，每句话都调云端大模型在经济上根本不成立。
>
> **一个关键设计**：我们**不是"用关键词/小模型判死"**，而是**分层放行**——
> 关键词层只有在**足够确信**时才定案（"转人工""投诉"这种几乎唯一指向的词），
> **不确定就往下走**。这是"高召回优先"的取舍。
>
> ⚠️ **而且我们为此付过代价**：本地小模型**冷启动十几秒**，
> 撞上统一的 8 秒超时 → **静默降级**（见 Q10）。
> **用小模型不只是"省钱"，还要为它的可用性设计**（预热、独立超时、降级路径）。

## 五、多 Agent 协作

### Q16. 多个子 Agent 之间如何进行通信和任务协作？

**标准答法**：两种范式

| | **编排（Orchestration）** | **协作（Choreography）** |
|---|---|---|
| 谁决定下一步 | 中心调度器 / 代码 | 各 Agent 自己决定，靠消息传递 |
| 优点 | 可控、可审计、成本可预测 | 灵活、能处理未知情况 |
| 缺点 | 不够灵活 | 难调试、容易死循环、成本不可控 |
| 常见形态 | 主 Agent 调子 Agent（supervisor / handoff） | 消息总线 / 黑板 / 共享状态 |

**通信内容**通常三类：**任务委派**（去干什么）、**结果回传**（干得怎么样）、
**共享状态**（大家都需要的上下文）。

**落到本项目——我们是纯编排，而且是有意的**：

> **我们没有 Agent 之间的自由通信**。跨域问题走 `CompositeGraph`：
> **代码**判定"命中了 ≥2 个业务域" → **代码**决定扇出哪几个 Agent →
> 各域**并行**跑自己的 ReAct → 结果汇到 `synthesize` 节点 → 生成一条综合回答。
>
> **为什么选编排**：
> 1. **可审计**——客服场景要能回答"这句话为什么交给了这几个 Agent"；
> 2. **成本可预测**——扇出 2 个还是 3 个是自己算的，不是模型决定的；
> 3. **不会死循环**——扇出是固定的，没有 Agent 互相喊话的可能。
>
> **代价也说清楚**：**不能动态决定要不要叫某个 Agent**——
> 如果一句话里"设备"的信号很弱，我们照样会把它扇出去（因为关键词层判了 ≥2 个域）。
>
> **⚠️ 一个真实的技术细节**（面试官如果追问 LangGraph4j，这条很加分）：
> **LangGraph4j 的并行没有公开 API**。翻遍 `StateGraph` 只有
> `addEdge(String, String)`，没有多源汇合的重载。真相是**隐式**的：
> **给同一个源节点挂多条出边**，编译期自动生成并行合成节点；
> 而且**所有分支必须汇合到同一个后继**，否则 `compile()` 直接抛错。
> （`ParallelNode` 是 public 的，但它由编译器生成，不该自己 new。）

### Q17. 如果多个 Agent 同时修改同一个文件，如何避免冲突？

**标准答法**（这题问的是**共享可变态的并发控制**，本质和分布式写冲突是一回事）：
1. **减少共享**——让 Agent 尽量无状态、各写各的（**最好的解法**）；
2. **串行化**——同一资源的操作排队（锁 / 队列 / 单写者）；
3. **乐观并发**——版本号 / CAS，提交时校验没被别人改过；
4. **幂等 + 去重**——重复提交不产生副作用（**幂等键**）；
5. **人审兜底**——高风险写操作不自动落地，走确认。

**落到本项目**：

> **我们没有"多个 Agent 改同一个文件"这个场景**，但**有同构的问题**：
> **同一个会话里的共享可变状态**。而且我们的处理方式正好覆盖了上面 5 条：
>
> | 共享状态 | 怎么防冲突 |
> |---|---|
> | **发布草稿**（同一会话） | **① 减少共享**：只有 PublishAgent 写，其它 Agent 只读；<br>**② 串行化**：同一个人在一个会话里对话天然串行； |
> | **落库提交** | **④ 幂等 + 去重**：**一次性确认令牌**——有有效期、且**用过就作废**。<br>用户重复点"确认"不会写两遍；抄错令牌会被拦下（说明他可能在看着另一条发布的摘要） |
> | **会话粘性**（Redis，每轮都写） | **③ 乐观**：按 `conversationId` 为键，**同一会话串行**，不存在并发写同一 key |
> | **业务库（`jxj`）** | **① 减少共享**：**所有查询 Agent 对业务库只读**——只读 Mapper 与写入 Mapper **分包**，从结构上杜绝查询路径顺手写数据 |
>
> **最核心的一条设计**：**由 Agent 驱动的写路径只有发布一条，而且它是确定性状态机。**
> 写操作不经过 ReAct（模型不能决定写什么、什么时候写），
> 所以**根本不存在"两个 Agent 同时想写"的可能**。
> （其余写入——审计日志、飞轮收集、管理台的知识库上传——都不在 Agent 的对话链路上。）
> **"没有并发冲突"不是因为锁做得好，是因为共享面被设计得很小。**
>
> **⚠️ 边界**：如果将来要支持"多端同时编辑同一个草稿"（比如 App 和网页同时开着），
> 现在的按会话串行就不够了，需要加**版本号 + 冲突提示**。
> 我们没做，因为现在没有多端编辑的产品需求。

## 六、开放题

### Q19. 如果让你优化一个 Coding Agent 系统，你会优先从哪些方向入手？

**标准答法**（按优先级，**别一上来说"换个更强的模型"**）：

1. **先做可观测性**——不知道它错在哪，优化就是猜。
   每步的输入输出、工具调用、耗时、token、失败原因都要能看见；
2. **建评估集，量出错在哪**——**没有量尺的优化都是玄学**。
   按失败类型分桶（路由错？检索错？工具用错？上下文丢信息？），先打最大的那桶；
3. **降低单步成本**——路由前置（能用小模型/规则的别上大模型）、
   工具结果裁剪、prompt cache；
4. **收窄工具与上下文**——工具描述写清边界、只给该给的；
5. **兜底与收敛**——步数上限、重复调用检测、失败降级；
6. **最后才是换模型/调提示词**。

**落到本项目——我们就是这么干的，而且有两条真实经历可以讲**：

> **第一条经历：先做可观测性，再谈修问题。**
> 我们踩过一次"**静默失效**"：本地小模型冷启动十几秒，撞上 8 秒统一超时，
> 两层双双超时 → 这句话被判 `UNKNOWN` → **静默降级到兜底**。
> **用户只觉得"答得敷衍"，从现象上根本看不出是超时。**
> 这个坑逼出的改动是：**审计表里必须先记下分类依据**
> （`ai_audit_log` 记意图、置信度、**命中层**、路由阶段）。
> 同类问题还有：会话粘性把完整新问题当追问吃掉——
> 也是靠审计里 `stage=sticky` 才定位到的。
> **所以"先做可观测性"对我是具体的，不是口号。**
>
> **第二条经历：先补量尺，再改代码。**
> 我们的意图评估集原来只有 26 条，报 **96.2%**，看着挺好。
> 扩到 **63 条**（加"发布 vs 查询""跨域 vs 不该跨域"两组对照）后，
> **同一套代码**只有 **87.3%**——**不是系统变差了，是原来的尺子量不出来**
> （旧集合里"发布"只有 1 条，且恰好是词表专门为它写过的说法，**改坏了也看不出来**）。
> 补完量尺后一轮轮修，最后到 **96.8%**。
>
> **最近还多了一条：写完的数字要能复跑，而且要真的去复跑。**
> 我们文档里记的检索 Recall@5 是 95.8%，用户质疑"太夸张了吧"，一复跑只有 **87.5%**——
> 因为那个数字测于**16 篇的小语料**，而且**只量到融合层**，没量线上真正在用的
> "召回 20 → 精排 → 取 5" 流水线口径（**83.3%**）。
> 顺带还揪出一个真缺陷：关键词检索**只搜正文**，
> 而库里 16/22 篇的**标题才是问句**——用标题原话搜，它自己的文档连前 6 都进不去。
> **所以我会把"评估是否可以复跑、多久复跑一次"也放进优化清单——
> 数字会过期，而且不会自己报警。**

> 详细答法和完整故事见 `简历与面试-主文档.md` 第七节，这里只放骨架。

| 问题 | 一句话答法 |
|---|---|
| **怎么保证模型不编平台规则？** | 三层：**证据闸**（生成**前**，资料不够就不让开口）→ 提示词硬约束 → 生成后**自评**。另加数据飞轮收集答不上来的问题。**闸必须在生成前**——生成完再撤回，错话已经说出去了 |
| **证据闸凭什么有效？** | 标 34 条样本**画阈值曲线**，发现**向量相似度两类区间完全重叠、根本没有可用分界点**（阈值 0.6 时漏放率 100%）→ 换**精排**做判据。**关键是"用数据发现判据选错了"，不是调参调出来的** |

| **为什么不用一个 Agent 挂所有工具？** | 两种都可行。单 Agent 的好处是跨域天然不是问题；我们没选，代价是明确的：**成本**（每轮都要把全部工具塞进上下文让大模型规划，我们现在 98% 请求不上云）、**权限**（工具白名单要运行时过滤）、**可审计**。**ReAct/plan 是"每轮多花一次大模型"换"不用做路由判定"** |
| **跨域怎么做到的？** | `CompositeGraph` 并行扇出 + 汇总。**执行层一直是好的，模型也判得出来**——真问题是**关键词层抢答、模型根本没轮到**。修法：别的**业务域**也在说话时不许抢答 |
| **你的 RAG 召回多少？** | **先讲口径**：线上流水线（召回 20 → 精排 → 取 5）**83.3%**，融合层 87.5%，纯向量 87.5%，纯关键词 70.8%。原来记的 95.8% 已作废（测于小语料 + 只量融合层） |
| **这套 RAG 还有什么不足？** | 六条，照实说：① 关键词路搜错字段（已定位未修）② 证据闸阈值没随语料重校准（当前漏放 10%）③ 没有 NLI 逐句校验 ④ 没有严格父子块（`parent_id` 建了但从未写入）⑤ 没有 Query 改写 ⑥ 指标只有 Recall@K |
| **转人工怎么实现的？** | **照实说：没真的入队。** `ai_handoff` 表建好了，但"转人工"目前只是一句固定话术。**这是项目里唯一一个"说了但没做"的功能** |
| **最难排查的问题是什么？** | **静默失效**那一类——功能"看起来能用"，只是悄悄做错了事。举三个：小模型冷启动导致静默降级、粘性把完整新问题当追问吃掉、兜底分支返回不可变 `List.of()` 让整篇 OCR 全丢。**共同点是都不报错**——所以习惯是**先做可观测性，再谈修问题** |

## 八、"这题我没做过"怎么答（通用策略）

**别硬蹭，也别摆烂**。用**三段式**：

> **① 先答通用原理**（这题的标准答案是什么）→
> **② 说我做过的最接近的事**（同构问题 + 具体取舍）→
> **③ 说清边界 + 如果要做我会怎么做**

**为什么这样答有效**：
- ①证明你**懂这题在问什么**，不是没听懂；
- ②证明你**做过工程**，不是只背过八股；
- ③证明你**知道边界、也能设计**——**面试官最怕的是"不知道自己不知道"**。

**几个现成的迁移对照**（这题问的是 A，你答 B，但要**先承认**再迁移）：

| 面试官问 | 你可以迁移到 |
|---|---|
| 多个 Agent 改同一个文件 | **同一会话的共享可变状态**（草稿 / 粘性 / 一次性令牌） |
| 上下文压缩 | **状态外置**——把该记住的搬出 context |
| 长期记忆 | **发布草稿的结构化状态** + 知识库（平台共享的"长期记忆"） |
| MCP | **`@Tool` + 能力注册表 + 角色白名单**，并说清什么时候该上 MCP |
| 工具返回过大 | **父子块 / 表格摘要**——"短的负责被找到，长的负责被读懂" |
| Prompt Cache | **天然符合的那几条 + 自己项目里破坏缓存的那一处** |

**最后一定要主动说的边界**（比假装都做完强得多）：
关键词路搜错字段（已定位未修）、证据闸阈值未重校准、NLI 没做、没有长期记忆与上下文压缩、
没有 MCP、转人工没真入队、没说步数上限。

**结尾可以反问面试官**（挑一个，说明你在想工程而不是在想背题）：
> "你们线上 Agent 的效果是怎么度量的？有没有类似评估集的东西，多久跑一次？"
> "工具规模大了之后，你们是走 MCP 还是自己维护注册表？"
