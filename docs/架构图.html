一、主流程图：一条消息从进来到返回

读法：①~⑦ 全是判定，所有判定最终都汇到 ⑧ 分派； ⑧ 之后才分岔成四条执行路。⑧ 是整个图唯一的汇聚点—— 代码里 identity / command / scan / known / classify / match 六个节点的出口，指向的都是它。 
flowchart TD
    START(["起点：用户发一句话"])
    START --> ID

    ID["① 身份检查<br/>查 MySQL 的 ai_user 表"]
    ID -->|"通过"| CMD
    ID -->|"拦下：未登录 / 账号不存在 / 账号停用"| D

    CMD["② 系统命令<br/>看是不是 /reset 这类指令"]
    CMD -->|"没命中"| SCAN
    CMD -->|"命中 /reset（顺带清 Redis 粘性）"| D

    SCAN["③ 开场扫描<br/>读粘性 + 关键词扫描 + 跨域判定<br/><b>三件事都是零成本，不叫模型</b>"]
    SCAN -->|"同时命中 ≥2 个业务域"| D
    SCAN -->|"关键词能定案"| KNOWN
    SCAN -->|"含「那台 / 它」+ 有上一轮"| D
    SCAN -->|"都不成立"| RESOLVE

    KNOWN["④ 关键词定案<br/>关键词判出的意图 vs 粘性里的意图<br/>一样沿用 / 不一样重新匹配"]
    KNOWN -->|"产出决策"| D

    RESOLVE["⑤ 指代消解<br/>用最近 5 轮把「那台」补成完整问题<br/>⚠️ 要叫一次本地小模型"]
    RESOLVE --> CLASSIFY

    CLASSIFY["⑥ 意图分类<br/>第1层 关键词加权 → 第2层 本地小模型 → 第3层 云端大模型"]
    CLASSIFY -->|"转人工 / 投诉"| D
    CLASSIFY -->|"模型判出多域"| D
    CLASSIFY -->|"正常"| MATCH

    MATCH["⑦ 匹配助手<br/>能力注册表 + 角色白名单 + 优先级<br/>匹配不到就用兜底助手（不挂任何工具）"]
    MATCH -->|"产出决策"| D

    D["⑧ 分 派 ◆<br/>① 先把「这句是啥意图、交给谁」推给前端<br/>② 再由条件边决定走哪条执行路<br/><b>⚠️ 审计在这之前已经落库</b>"]
    D -->|"短路：只回一句话"| E
    D -->|"知识类 → 问平台规则"| K1
    D -->|"跨域 → 一句话问了多个域"| C1
    D -->|"单域 → 正常查数据"| A1

    subgraph KG ["⑨ 知识线作答 — ⚠️ 不是 Agent，是代码写死的流水线"]
        direction TB
        K1["① 混合召回 20 条<br/>关键词 BM25 + 语义 KNN，RRF 融合"]
        K2["② 精排打分<br/>交叉编码器 gte-rerank-v2"]
        K3{"③ 证据闸<br/>分够不够回答？"}
        K4["回兜底话术<br/>+ 记进数据飞轮"]

        K8["出答案 + 溯源依据 sources"]

        K3 -->|"不够"| K4

图上标了三个 ⚠️，那是这张图最值钱的地方

标记含义
⑨ 不是 Agent押金 / 租金这类问题走的是代码写死的流水线——为了"资料不足不许答"放弃了灵活性
⑩ 真并行三个域同时跑，不是排队；结果各写各的，最后一起收
⑪ 这才是 Agent循环在 ②↔③：模型自己决定调几次工具、什么时候停手

两条很容易讲错、图上特意标出来的顺序

  • 审计在 ⑧ 之前（不是之后）——推给前端的和审计记下的必须是同一份判定
  • 存用户消息在图之后——放前面的话，⑤ 指代消解会把这一句自己读进去

二、为什么知识线不做成 Agent

这是整个项目里最值得讲的一个设计判断。两张图对比：

flowchart LR
    subgraph BAD["如果知识线做成 ReAct Agent"]
        direction TB
        B1["模型拿到问题<br/>「押金怎么退」"] --> B2{"要不要调检索工具？"}
        B2 -->|"模型想：<br/>这个我训练数据里见过"| B3["不查资料<br/>直接凭印象答"]
        B2 -->|"决定查"| B4["检索 → 精排 → 证据闸"]
        B3 --> B5["❌ 编出一条平台规则<br/>用户拿到自信满满但错误的答案"]
        B4 --> B6["✅ 正确答案"]
    end

    subgraph GOOD["实际：知识线是代码写死的流水线"]
        direction TB
        G1["用户问题"] --> G2["代码强制：先召回"]
        G2 --> G3["再精排"]
        G3 --> G4["再过证据闸"]
        G4 -->|"资料不够"| G5["✅ 直接回兜底话术<br/>模型压根没机会开口"]
        G4 -->|"资料够"| G6["✅ 生成答案"]
    end

    style BAD fill:#f8cecc,stroke:#b85450
    style GOOD fill:#d5e8d4,stroke:#82b366

判据不是"这条线上有没有调模型"，而是"下一步由谁决定"。

知识线（工作流）如果做成 ReAct Agent
能跳过检索吗不能，顺序写死能
能绕过证据闸吗不能，闸在生成之前能
会编平台规则吗不会可能

三、四张图怎么串起来的

flowchart TD
    HTTP["HTTP 请求"] --> CS["对话服务 ChatService"]
    CS --> RG["<b>路由状态图 RoutingGraph</b><br/>11 节点 / 5 条件边"]

    RG -->|"知识类"| KL["知识线<br/>（不是图，是一条 Java 链）"]

    CG -->|"每个域节点内部调用"| RA

    PA["发布助手 PublishAgent"] -.->|"独立一条线<br/>不在上面任何图里"| PG["发布图 PublishGraph<br/>4 节点 + interrupt 挂起点<br/>+ MySQL 检查点"]

    style RG fill:#ffe6cc,stroke:#d79b00,stroke-width:2px
    style PG fill:#fff2cc,stroke:#d6b656

"谁决定走向"总结（这是项目的设计主线）：

图谁决定下一步用到的 LangGraph 能力
RoutingGraph代码条件边 ×5、dispatch 汇聚、recursionLimit(20)
CompositeGraph代码（决定扇出）隐式并行节点、appender 通道、扇入
ReactAgent ×4模型库预置 ReAct 循环、工具调用
PublishGraph代码interrupt 挂起 + checkpointer

四、发布：另一条独立的线（human-in-the-loop）

flowchart TD
    U(["用户：帮我发布一台出租"]) --> H

    H["handle<br/>抽字段 + 校验"]
    H -->|"字段没齐"| ASK["追问缺什么<br/>（模型只负责抽字段）"]
    ASK --> E1(["⏹ 结束（这一轮到此为止）"])

    H -->|"字段齐了"| SUM["给确认摘要 + 一次性验证码"]
    SUM --> INT{{"☆ interrupt 挂起 ☆<br/>图停在这里等人<br/>状态写进 ai_graph_checkpoint<br/>⚠️ 进程重启也不丢"}}

    INT -->|"用户下一轮回复"| BR{"用户说了什么？"}
    BR -->|"取消"| CN["作废草稿"]
    BR -->|"补充 / 修改"| H
    BR -->|"确认发布"| W["校验验证码<br/>（有效期 + 是否用过）"]
    W -->|"验证码不对"| WARN["提示核对"]
    W -->|"通过"| WRITE["落库，进入待审核"]
    CN --> E2(["⏹ 结束"])
    WARN --> E2
    WRITE --> E2

    style INT fill:#fff2cc,stroke:#d6b656,stroke-width:3px
为什么这里必须用 checkpointer：图挂起后，下一轮请求得从挂起点恢复—— "挂在哪"必须有地方存。库里只自带 MemorySaver（重启就没，和项目"状态必须活过重启"的原则冲突） 和 FileSystemSaver（写本地磁盘），所以自己实现了一个 MysqlCheckpointSaver。

五、数据存在哪

flowchart LR
    subgraph W["一轮对话会写这些"]

        W1["审计一条 → ai_audit_log<br/>（在 ⑧ 之前就写了）"]

存储存什么谁在用
MySQL jxj212 张业务表（只读，Mapper 分包隔离）+ 18 张 ai_ 表全部
Redisai:token:* 登录令牌、ai:sticky:* 会话粘性（TTL 30 分钟）鉴权、路由
Elasticsearchjxj_knowledge：22 篇 / 233 个切片（IK 分词 + 1024 维向量）知识线
本地磁盘data/knowledge-files/：上传的原件（按内容指纹命名）答案溯源跳转

⚠️ ES 里还有个 knowledge_base 索引（42 篇）是别的项目留下的，别动。

六、名词对照

代码里的名字中文
RoutingGraph路由状态图（本项目骨架，11 个节点）
CompositeGraph跨域综合图
PublishGraph发布图
dispatch分派（唯一汇聚点）
resolve指代消解
classify意图分类
synthesize汇总（各域结果合成一条）
interrupt挂起（图停在那等人）
checkpointer检查点（把挂起状态存下来）
state / node / edge状态 / 节点 / 边
条件边conditional edge，按条件决定下一个节点
reducer / 通道多个节点写同一个字段时的合并规则
扇出 / 扇入fan-out / fan-in
ReAct推理 + 行动循环（模型想一步 → 调工具 → 看结果 → 再想）
Agent智能体：模型决定下一步
Workflow工作流：代码决定下一步
BM25 / KNN关键词检索 / 语义（向量）检索
rerank精排
RRF倒数排名融合（把两路检索结果合成一份）
证据闸判断"资料够不够回答"的那道关
