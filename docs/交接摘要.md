## 五、核心设计原则（要背）

**① 向量化的是「入口」，不向量化的是「本体」——但本体必须存**
「不向量化」≠「不存」。本体（表格 markdown、父块全文）一律**结构化存库**，靠 `tableId` / `section_path` 取回。

**② 父子块 和 表格，是同一个模式的两次应用**

```
        检索入口（向量化）      本体（不向量化，取回来用）
第一处：  子块                  父块
第二处：  表格摘要              表格本体
```
因为**检索要短而准（长了向量表征就糊），生成要全而完整（缺表头就答错）**。

**③ 融合排序 ≠ 相关性排序** —— RRF 的 `1/(60+名次)` 是累加的，天生偏爱"两路都靠前"，会低估"只在单路极端靠前"的。**融合管"别漏"，精排管"挑准"，不能合成一步。**

**④ 双塔适合排序、不适合判定** —— 向量相似度是"各自算好再比"，对"资料到底有没有回答这个问题"不敏感。

**⑤ 判据选错比阈值调错严重** —— 画曲线的价值是能看出"**选不出来**"。

## 八、硬规矩（别踩）

| 规矩 | 为什么 |
|---|---|
| **杀进程只按 PID** | `taskkill /F /IM java.exe` 会连 ES 和 IDEA 一起杀（踩坑第 28 条） |
| **我起的应用用完自己杀** | 否则占着 8082，用户 IDEA 起不来 |
| **别在应用运行时跑 `mvn`** | 会清空重建 `target/classes` → `ClassNotFoundException`（第 40 条） |
| **`.env` 的初始密码改了不生效** | 只在"一个 ADMIN 都没有"时建号；改用 `POST /api/auth/password` |
| **测试数据物理删** | `deleteById` 走逻辑删除清不干净 |
| **改 PATH 后重开终端** | 已开着的 shell 拿不到新值 |
| **导中文 SQL 加 `--default-character-set=utf8mb4`** | 否则按 GBK 读，注释写坏 |
| **跑完测试索引数不应变** | 变了说明清理漏了，会污染检索 |
